## 5. `SO_REUSEPORT`: что подтверждено и что из этого следует

**Подтверждено исходниками тега v26.9.9:**

1. `transport/internet/system_listener.go`: в `getControlFunc` после применения socket options вызывается `setReusePort(fd)` — **безусловно**, без проверки `sockopt`; результат не проверяется.
2. `transport/internet/sockopt_linux.go`: `setReusePort` устанавливает `SO_REUSEPORT` = 1; при ошибке возвращает ошибку с уровнем warning.
3. `lc.Control` назначается только для `*net.TCPAddr`; для `net.UnixAddr` он равен `nil`, то есть к unix socket `SO_REUSEPORT` не применяется.
4. `app/commander/commander.go` вызывает `internet.ListenSystem(ctx, addr, nil)` — `sockopt` равен `nil`, но `setReusePort` всё равно выполняется.

**Следствия:**

| Ситуация | Поведение |
|---|---|
| Порт занят listener'ом без `SO_REUSEPORT` | bind не проходит; `commander.Start` возвращает ошибку; `Instance.Start` прерывается на первой ошибке feature; Xray не запускается |
| Порт занят listener'ом с `SO_REUSEPORT` (второй экземпляр Xray того же эффективного UID) | bind может пройти; оба процесса принимают на одном адресе и порту; ядро распределяет входящие соединения между ними |
| Распределение gRPC-соединений | по правилам ядра для группы `SO_REUSEPORT`; конкретное соединение может попасть в любой процесс группы |
| Достаточность проверки свободного порта | нет: она не исключает гонку и не доказывает единственность экземпляра |

Поэтому архитектурно зафиксировано: одновременно работает только один управляемый экземпляр Xray, старый процесс останавливается до запуска нового, совместное использование порта недопустимо. Собственный механизм блокировки не изобретался: lock/PID-контракт обозначен как требование будущей реализации, проверяется в слое запуска (Core/procd) и сценарием 137.

## 6. Last-good, rollback и procd при отказе запуска

Разделены: last-good на Flash, попытка запуска новой конфигурации, ошибка запуска процесса, попытка восстановления last-good, повторный отказ по той же причине, `ENGINE_DOWN`, поведение procd, сохранение сетевой политики (№20 §8.2).

Ключевые инварианты:

1. Политика не удаляется из-за того, что Xray не запустился.
2. VPN-предназначенный трафик не уходит в DIRECT молча.
3. Last-good не обязан восстановиться, если использует тот же занятый `api.listen`; успех отката — только подтверждённый запуск.
4. Запись last-good не является подтверждением работающего движка.
5. Отсутствие процесса обнаруживается по S2 (procd/ubus и проверка процесса), а не по тексту ошибки API.
6. Пока процесса нет, отказ не публикуется как `api_error`.
7. Число и интервал попыток procd не назначаются: это параметр реализации `[Т]`.

Отдельно зафиксировано: при запуске через procd приложение не получает исходную ошибку `commander.Start` автоматически; точный механизм передачи причины (`[Т]`) не выдуман.

## 7. Формула свежести

```
fresh ⇔ now − last_try_time ≤ TTL
TTL   = T_cycle + grace

T_cycle ≤ probeInterval + 2 × max_probe_time          (enableConcurrency: true)
T_cycle ≤ N × (probeInterval + max_probe_time)        (enableConcurrency: false)
```

Обоснование множителя 2: в конкурентном режиме все пробы цикла стартуют одновременно, Observer ждёт последнюю и только затем выполняет `Sleep(probeInterval)`; одна и та же запись может завершиться первой в цикле k и последней в цикле k+1, поэтому интервал равен `probeInterval + d_max + d_next − d_пред ≤ probeInterval + 2 × d_max`. Прежняя формула `probeInterval + max_probe_time` была нижней оценкой.

В последовательном режиме пауза выполняется после каждой пробы, включая последнюю, поэтому цикл равен сумме длительностей и `N` пауз.

`grace` — параметр реализации `[Т]`: численное значение не утверждено, требуется измерение на целевой сборке. До измерения TTL не считается подтверждённым на AX3000T.

## 8. Определение `N`

`N` — количество outbound, фактически попавших в выборку `outbound.HandlerSelector.Select(subjectSelector)` после префиксного сопоставления тегов. Это не количество литеральных элементов массива `subjectSelector`: один префикс может соответствовать нескольким серверным outbound. Формулировка синхронизирована в №18 §7.2.1, №20 §7.2, REQ-168 и сценарии 135.

---

## 9. Правило смешанной свежести

1. Свежесть считается по каждой записи отдельно, по её собственному `last_try_time`.
2. Отсутствующая запись и `last_try_time = 0` → `no_data`, не `stale`.
3. `observability.state = ok` при наличии хотя бы одной свежей записи; `stale` — только если свежих записей нет; `no_data` — список пуст; `error` — вызов не удался.
4. Список не объявляется свежим из-за одной записи и не объявляется устаревшим целиком при частично свежих данных.
5. Вердикт доступности (`no_candidate`, `fallback_expected`) строится только по свежим записям; устаревшие исключаются.
6. `delay = 99999999` — сентинел «не измерено», а не задержка.
7. Новых внешних статусов не вводилось: смешанное состояние выражается существующими `state` и `fresh`. Введение отдельного агрегата меняло бы утверждённую семантику интерфейса и потребовало бы решения владельца; такого решения не запрашивалось и не подразумевалось.

## 10. Дедлайн gRPC и нормализация кодов

| Код | Когда | Куда публикуется |
|---|---|---|
| `unimplemented` | сервис не зарегистрирован (опечатка, пустой список сервисов) | `observability.error_code`, `observability.state=error` |
| `deadline_exceeded` | истёк конечный дедлайн RPC | `observability.error_code`, `state=error` |
| `api_error` | иная ошибка вызова при работающем Xray | `observability.error_code`, `state=error` |
| `engine_down` | процесса Xray нет | состояние процесса (S2) и состояние сервиса `DEGRADED/ENGINE_DOWN`; не код `observability` |

Вызов выполняется с конечным дедлайном (`context.WithTimeout`); численное значение — `[Т]`. Таймаут не обновляет `last_try_time`, поэтому не «освежает» данные: после серии таймаутов записи становятся `stale` по TTL. Имена gRPC-статусов в полях приложения не используются.
