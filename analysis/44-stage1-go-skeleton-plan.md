## 1. Цель этапа

Подготовить минимальный каркас Go-демона и основу LuCI-интеграции без включения реальных сетевых функций.

Проверяемый результат этапа: демон запускается и останавливается через procd, читает и валидирует конфигурацию, публикует статус через ubus, пишет структурированные логи, корректно обрабатывает сигналы и ошибки, а внутренние контракты покрыты unit-тестами. Ни одно действие этапа не меняет nftables, маршрутизацию, DNS, Xray и состояние роутера.

Что этап 1 **не** доказывает: работоспособность перехвата, поведение Xray Observatory и gRPC, пригодность выбранного механизма исключения трафика роутера, работу на AX3000T. Эти вопросы остаются в №45 категориями «требует технической проверки» и «блокирует выпуск».

## 3. Основные контракты

Ниже — проект контрактов для обсуждения; код не создаётся. Формулировки согласованы с №11.

### 3.1 Core / application lifecycle

```go
// проект, не реализация
type Core interface {
    Start(ctx context.Context) error        // инициализация по порядку §4
    Stop(ctx context.Context) error         // штатное завершение
    Status() Snapshot                       // runtime-снимок для API
    Submit(op Operation) (opID string, err error) // очередь изменений, один mutex
}
```

Инварианты: `Start` идемпотентен; повторный `Start` при работающем ядре — ошибка `VM_ERR_INVALID_STATE`; `Submit` при активной операции возвращает `VM_ERR_BUSY`.

### 3.2 Конфигурация

```go
type Config struct {
    SchemaVersion int
    Intent        Intent          // enabled | disabled
    Strategy      string          // random | roundRobin | leastPing | leastLoad
    DirectOnFailure bool          // по умолчанию true
    UDPSAllowlist []PortRange     // только чтение на этапе 1
}
```

Правила: `SchemaVersion` обязателен; неизвестные поля — ошибка валидации, а не молчаливое игнорирование; значения по умолчанию применяются при чтении; запись только атомарная и только через Storage.

### 3.3 Состояние VPN Manager

```go
type Signal struct {
    Name    string     // S1..S6
    Value   string
    At      time.Time  // для вычисления свежести
    Known   bool
}
type Snapshot struct {
    State      string      // DISABLED_BY_USER | STARTING | ACTIVE | DEGRADED | UNKNOWN
    Reason     string
    Signals    []Signal
    ObservedAt time.Time
}
```

На этапе 1 реально вычисляется только S1 (намерение из конфигурации); остальные признаки помечены `Known=false`, поэтому состояние выше `STARTING` не поднимается. Это осознанное ограничение, а не дефект.

### 3.4 Диагностика

```go
type Report struct {
    Version      string
    SchemaVersion int
    State        Snapshot
    Warnings     []string   // например: "not_implemented: policy"
}
```

Диагностика только читает и никогда не меняет состояние (№10 A12).

### 3.5 Граница IPC/API

- Один ubus-объект `vpnmanager` с методами `status`, `operation` на этапе 1.
- Ответы соответствуют конверту и кодам №12 §1–§2; ошибка — код + человекочитаемое сообщение.
- Демон повторно проверяет права вызывающего и не доверяет ACL как единственной защите (№11 §2).
- Метод, которого нет в реестре №12 §6, не регистрируется; вызов → `VM_ERR_UNSUPPORTED`.

### 3.6 Logging

```go
type Logger interface {
    Debug(msg string, kv ...any)
    Info(msg string, kv ...any)
    Warn(msg string, kv ...any)
    Error(msg string, kv ...any)
}
```

Требования: уровни; ключ-значение без форматных строк из пользовательских данных; маскирование секретов до записи; отсутствие записи `access.log`/`error.log` Xray (это отдельная функция этапа 3 и штатный `logrotate`, №11 §12).

### 3.7 Error handling

- Все ошибки — типизированные значения с кодом `VM_ERR_*`; сравнение по коду, не по тексту.
- Ошибка не глотается: либо возвращается вызывающему, либо логируется с кодом и переводит состояние в `DEGRADED` с причиной.
- Паника в модуле перехватывается на границе Core и не завершает процесс молча (№11 §1).

### 3.8 Взаимодействие с LuCI

- Вью вызывает только `vpnmanager.*` через rpcd; прямых обращений к файлам и процессам нет.
- Подписка на `vpnmanager.event` вместо частого опроса; на этапе 1 публикуется только `state`.
- Устаревшие данные помечаются временем наблюдения; «нет данных» отображается как «нет данных», а не как «всё хорошо».

## 4. Lifecycle

### 4.1 Последовательность

1. **Запуск.** procd запускает один instance демона. Демон не является владельцем `flock` Xray: singleton Xray относится к launcher'у Xray и реализуется на этапе 3 (решение владельца №4).
2. **Загрузка конфигурации.** Чтение файла конфигурации через Storage; отсутствие файла — штатный первый запуск с `intent=disabled`.
3. **Проверка конфигурации.** Валидация схемы, версии и значений; ошибка → состояние `config=Invalid`, демон остаётся запущенным и отдаёт причину через API (не падает и не перезаписывает файл).
4. **Инициализация компонентов.** Порядок: logging → storage → config → state → заглушки модулей → api. Каждый шаг либо успешен, либо прекращает старт с кодом ошибки.
5. **Готовность.** Регистрация ubus-объекта, публикация первого `state`; только после этого демон считается готовым.
6. **Обработка сигналов.** `SIGTERM`/`SIGINT` — штатное завершение; `SIGHUP` на этапе 1 не перезагружает конфигурацию (перезагрузка — через procd `reload`), а логирует и игнорируется.
7. **Штатное завершение.** Прекращение приёма запросов, ожидание текущей операции с таймаутом, снятие регистрации ubus, закрытие файлов, код выхода 0.
8. **Аварийное завершение.** Паника или необработанная ошибка → запись в лог с кодом, ненулевой код выхода; процесс перезапускает procd.
9. **Восстановление после перезапуска procd.** Демон не хранит «активное» состояние как флаг: при старте состояние вычисляется заново из конфигурации и признаков; незавершённая операция отбрасывается с записью в журнал (№11 §11).

### 4.2 Утверждённые решения, которые этап 1 не меняет

- `respawn 3600 5 5` — конфигурация procd для сервиса; после серии быстрых отказов respawn прекращается, сервис остаётся остановленным.
- Singleton Xray — единственный launcher с kernel `flock` на `/var/run/vpn-manager/xray.lock`, `LOCK_EX|LOCK_NB`, без `FD_CLOEXEC`, PID-файл только для диагностики. На этапе 1 launcher не создаётся.
- Отсутствие DIRECT при отказе и сохранение политики перехвата — модель этапа 3; этап 1 её не реализует и не имитирует.

### 4.3 Что требует технической проверки позже

| Аспект | Почему не подтверждён | Где проверяется |
|---|---|---|
| Сохранение `flock` через `execve` и удержание блокировки Go-процессом | свойство ядра и реализации launcher'а | №45 RT-05, сценарии 146–150 |
| Поведение `respawn` целевой версии procd | версия procd сборки не подтверждена | №45 RT-06, сценарии 144–145 |
| Фактический порядок остановки procd и доставка `SIGTERM` | зависит от init-скрипта и procd | этап 3 |
| Время старта демона и влияние на бюджет apply | не измерялось | W-04 |
| Поведение при нехватке памяти | не измерялось | №45 RB-06 |
| Реакция ubus на переподключение UI во время операции | требует проверки на устройстве | W-11/W-13 |

## 6. Критерии приёмки этапа 1

Критерии сформулированы как проверяемые утверждения. Ни один не выполнен.

### 6.1 Готовность структуры

1. Репозиторий содержит перечисленные в §2 каталоги; пустых «на будущее» пакетов без интерфейса нет.
2. `gofmt -l` пуст, `go vet ./...` без замечаний, `go build ./...` успешен локально.
3. Ни один пакет не вызывает внешние бинарники (`nft`, `ip`, `xray`) — проверяется поиском по импортам и `exec`.
4. Сборка не требует сети после первичной загрузки зависимостей (используется только стандартная библиотека).

### 6.2 Корректность контрактов

1. Интерфейсы Core, Config, State, Diagnostics, Logger, API реализованы и описаны в godoc.
2. Валидация конфигурации отвергает: неизвестную `schema_version`, неизвестные поля, недопустимую стратегию, `direct_on_failure` вне bool; каждая ошибка имеет код `VM_ERR_*`.
3. `Snapshot` не может быть `ACTIVE` при `Known=false` для S2–S4 и S6 (проверяется unit-тестом).
4. Диагностика не изменяет файлов и состояния (проверяется сравнением хэшей до/после вызова).
5. Метод вне реестра №12 §6 возвращает `VM_ERR_UNSUPPORTED`, а не `VM_ERR_INTERNAL`.

### 6.3 Lifecycle

1. Демон стартует, публикует первый `state` и корректно завершается по `SIGTERM` с кодом 0.
2. Повторный `Start` при работающем ядре возвращает `VM_ERR_INVALID_STATE`.
3. Ошибка конфигурации не приводит к падению: состояние `config=Invalid`, причина доступна через API.
4. Паника в заглушке модуля не завершает процесс молча: фиксируется код и состояние `DEGRADED`.
5. После перезапуска процесс не остаётся в промежуточном состоянии: состояние вычисляется заново.
6. init-скрипт содержит `respawn 3600 5 5` и не запускает второй instance.

### 6.4 Unit-тесты

1. Покрыты: валидация конфигурации (включая негативные случаи), вычисление состояния по признакам, коды ошибок, очередь операций (BUSY/идемпотентность), атомарная запись Storage.
2. Тесты не требуют root, сети и роутера; запускаются одной командой.
3. Нет тестов, которые «проходят» за счёт пропуска проверок или `t.Skip` без причины.

### 6.5 Документация

1. `analysis/44` и `analysis/45` остаются актуальными; расхождения фиксируются отдельным отчётом, а не правкой «по факту».
2. В README/№00 отражено фактическое состояние: этап 1 начат/завершён, что проверено, что нет.
3. Ни один документ не объявляет `[Т]`-проверки выполненными.

## 7. Зависимости и риски

### 7.1 Зависимости этапа 1

| Зависимость | Тип | Статус |
|---|---|---|
| Go toolchain целевой версии | техническая | не выбрана и не зафиксирована |
| procd и формат init-скрипта целевой прошивки | техническая | версия не подтверждена (`[Т]`) |
| rpcd/ubus и ACL на целевой прошивке | техническая | проверяется в W-11 |
| LuCI (JS-вью, ucode) на целевой прошивке | техническая | Lua-контроллеров нет — подтверждено этапом 1 |
| Согласованные контракты №11/№12 | документация | готовы, non-blocking замечания №47 не блокируют |

### 7.2 Риски, которые нельзя закрыть планированием

1. **Версия procd.** `respawn 3600 5 5` семантически сверен с upstream `service/instance.c`, но версия в целевой сборке не подтверждена; поведение при исчерпании retry на устройстве не наблюдалось.
2. **Сохранение `flock` через `execve`.** Требует проверки на целевой платформе: удержание блокировки Go-процессом и отсутствие `FD_CLOEXEC` — свойство реализации launcher'а, а не документации.
3. **Ресурсы.** Бинарник ≤ 12 МБ, RSS ≤ 25 МБ — проектные ориентиры, не измеренные значения; skeleton может показать другую базу.
4. **ubus/ACL.** Поведение штатных ACL и повторная авторизация в демоне на целевой прошивке не проверены.
5. **LuCI JS.** Наличие ucode-контроллеров и отсутствие Lua подтверждены на этапе 1 read-only; совместимость с версией LuCI целевой сборки — `[Т]`.
6. **Соблазн имитации.** Заглушки не должны возвращать «успех»: это создаёт ложное впечатление проверенной функциональности и прямо запрещено правилами проекта.

### 7.3 Что этот план не решает

Этап 1 не отвечает на вопросы перехвата, fail-closed G1–G7, Observatory, `leastPing`/`leastLoad`, `fallbackTag`, UDP allowlist, DNS при `FALLBACK_BLOCK`, nftables и исключения повторного захвата. Все они перечислены в №45 и остаются открытыми до этапа 3 и окон W-02…W-15.
