## 3. Реализованные контракты

- **Entry point.** `vpnmand` работает в foreground, флаги `-config`, `-state-dir`, `-log-level`, `-version`; коды выхода 0/1/2; фоновых задач и демонизации нет.
- **Core lifecycle.** Порядок: загрузка и проверка конфигурации → регистрация компонентов → `Start` в порядке регистрации → публикация снимка состояния → готовность (`Ready`) → ожидание сигнала/отмены контекста → `Stop` в обратном порядке с таймаутом на компонент. Сбой старта откатывает уже запущенные компоненты; повторный `Start` и регистрация после старта отклоняются (`VM_ERR_INVALID_STATE`).
- **Configuration.** Поля `schema_version`, `intent`, `strategy`, `direct_on_failure`, `udp_allowlist`; значения по умолчанию — `intent=disabled`, `strategy=random`, `direct_on_failure=true`; неизвестные поля и отсутствие `schema_version` — `VM_ERR_VALIDATION`; отсутствие файла — штатный первый запуск со значениями по умолчанию. Конфигурация не записывается и не изменяется.
- **State / Snapshot / Report.** Состояния и признаки S1–S6 объявлены по №10 §5; снимок содержит состояние, причину, признаки и время наблюдения; `Store` защищён `RWMutex`, отдаёт глубокие копии. Инвариант: `ACTIVE` без известных S2, S3, S4, S6 отклоняется (`VM_ERR_INVALID_STATE`). В этапе 1 вычисляются `DISABLED_BY_USER`, `STARTING`, `UNKNOWN`; `ACTIVE` недостижим, поскольку сетевые признаки не наблюдаются.
- **Logging.** Уровни `debug|info|warn|error`, единый формат `время уровень сообщение key=value`, поля `token`, `password`, `secret`, `key`, `uuid`, `url` маскируются; вывод в переданный `io.Writer` (stderr), удалённых приёмников нет.
- **Error handling.** Коды `VM_ERR_*` из №12 §1 плюс `VM_ERR_INVALID_STATE`; ошибка несёт код, операцию, описание и исходную причину, распознаётся через `errors.As`/`Unwrap`; ошибка подсистемы не меняет состояние VPN.
- **Очередь операций.** Одна активная операция; параллельный `Submit` — `VM_ERR_BUSY`; завершение неизвестной операции — `VM_ERR_NOT_FOUND`.
- **API boundary.** Методы `vpnmanager.status`, `vpnmanager.version`, `vpnmanager.operation`; ошибки передаются в теле ответа с кодом `VM_ERR_*`. HTTP-сервер и Unix-сокет не создаются.

## 4. Заглушки

`xray.Manager`, `policy.Manager`, `devices.Registry`, `subscriptions.Provider`, `profiles.Registry`, `txn.Manager` объявлены и реализованы заглушками: любая операция возвращает `VM_ERR_UNSUPPORTED` с указанием этапа, ни один метод не выполняет системных действий и не сообщает о работающей функциональности. Заглушки `policy`, `devices`, `subscriptions`, `profiles`, `txn` зарегистрированы как `core.Component` с пустыми `Start`/`Stop`; `xray.Stub` намеренно не компонент — у `Manager` своя пара `Start`/`Stop` с параметрами.

## 6. Отклонения от плана №44

1. **`internal/vmerrors` вместо `internal/errors`.** Имя пакета `errors` перекрывает стандартный пакет и делает импорт неоднозначным; поведение и коды соответствуют контракту.
2. **ubus-транспорт отсутствует.** Регистрация ubus-объекта требует `libubox`/cgo, а внешние зависимости в этапе 1 запрещены. Граница API реализована внутри процесса, файлы `luci/` подготовлены; LuCI при отсутствии объекта показывает сообщение о недоступности, а не вымышленное состояние.
3. **Конфигурация — минимальное подмножество полей.** Включены только поля, определённые для этапа 1; остальные добавляются вместе с потребителями. Формат не расширялся самостоятельно.
4. **`xray.Stub` не является `core.Component`** (см. §4).
5. **Снимок состояния не сохраняется на диск.** Контракт персистентности для этапа 1 не определён; пакет `storage` реализован и протестирован, но демон его не использует для записи.
6. **Singleton/flock не реализован.** Корректность `flock`, наследования дескриптора через `execve` и поведения Go runtime требует технического подтверждения (№44 §5, №45 RT); имитация проверки не выполнялась.
