## 2. Какие положения добавлены или исправлены

**Добавлено (утверждённые требования).**
1. Always DIRECT обходит **обычные** внешние Blocklists (реклама, трекеры, прочие обычные категории).
2. Always DIRECT **не отменяет** системные ограничения, блокировку `Malware` и блокировку `Phishing`.
3. Обычные профили маршрутизации и VPN для устройства с Always DIRECT не применяются (подтверждено, уже действовало).
4. Защищённые категории — **только** `Malware` и `Phishing`; расширение требует отдельного решения владельца.
5. Whitelist снимает только обычные блокировки; `Malware`, `Phishing` и системные ограничения он не отменяет.
6. Временное отключение Blocklists отключает только обычные категории; защищённые и системные ограничения действуют.
7. Единое конечное поведение на DNS и L3: угрозы блокируются на обоих уровнях, обычные категории обходятся при Always DIRECT на обоих; механизмы могут различаться.
8. UI при включении Always DIRECT: предупреждение, объяснение обхода обычных списков, сообщение о сохранении блокировки `Malware`/`Phishing`, краткое постоянное пояснение в карточке устройства.
9. OQ-05: пользовательский BLOCK не может блокировать системные защищённые домены; системный защищённый список имеет приоритет.

**Исправлено (противоречия).**

## 3. Как теперь определена таблица приоритетов

Числовые уровни P0–P9 **не перенумеровывались**: это сохранило ссылки в №11, №17, №19, №20, №22. Вместо этого введён **защищённый контур S**. **Актуализация 24.11.2026 (после ревью):** канонический порядок — **P0 → S1 → S2 → S3 → P4 → P1 → P2 → P3 → P5 → P6 → P7 → P8 → P9**; служебный трафик проверяется первым и не блокируется защищённым контуром (прежний порядок отменён).
**Исправлено в U7 (R-01):** в прежней редакции этого документа P1 стоял перед P4, и это позволяло прочитать «Always DIRECT обходит пользовательский BLOCK». Действующее правило — **P4 (User BLOCK) проверяется до P1**; формулировки прежней редакции являются историческим описанием и действующим правилом не являются (№21 §8.2).

| Уровень | Что | Результат | Переопределение пользователем |
|---|---|---|---|
| P0 | Служебный трафик проекта | не перехватывается и не блокируется S1–S3 | нет |
| **S1** | Системные ограничения и системный защищённый список | ограничение действует; BLOCK на системный домен отклоняется валидацией | нет |
| **S2** | `Malware` | **BLOCK** | нет |
| **S3** | `Phishing` | **BLOCK** | нет |
| **P1** | Always DIRECT (постоянный или overlay) | DIRECT; обходит правила DIRECT/PROXY профиля (P7/P8), UDP-политику, Quick Block и **обычные** списки (P6); **P4 не обходит** | да (режим, таймер) |
| P2 | Quick Block | BLOCK (UDP) | да |
| P3 | Временное отключение Blocklists | обычные списки не применяются; S1–S3 действуют | да (таймер) |
| P4 | Пользовательский BLOCK | BLOCK; проверяется **до** P1 — Always DIRECT его не отменяет (R-01) | да |
| P5 | Whitelist | снимает только обычную блокировку P6 | да |
| P6 | Внешние Blocklists — **обычные категории** | BLOCK | да |
| P7–P9 | Пользовательский DIRECT / PROXY / default | DIRECT / PROXY / default | да |

Порядок: **P0 → S1 → S2 → S3 → P4 → P1 → P2 → P3 → P5 → P6 → P7 → P8 → P9**; First Match Wins. P0 — только трафик демона (UID/GID, `SO_MARK`, статические IP-наборы); на пользовательский трафик не распространяется (№18 §3.0.1).

Почему сделано именно так: `Malware`/`Phishing` должны быть выше Always DIRECT, а обычные списки — ниже; при этом требовалось не трогать существующую нумерацию и семантику P2/P4/P5/P7–P9. Отдельный контур S — минимальное структурное изменение, которое выражает утверждённое поведение без произвольного переназначения приоритетов. Альтернатива (разрыв P6 на P6a/P6b) отвергнута: она ломает ссылки и хуже объясняет, что защищённый контур не является «пользовательским правилом».

Следствия, зафиксированные в №18:
- P1 выше P6 → обычные списки обходятся (утверждено);
- S2/S3 выше P1/P3/P5 → угрозы блокируются при любом режиме, whitelist и временном отключении;
- **P4 выше P1** (User BLOCK действует при Always DIRECT) и выше P5/P6, но ниже S1–S3;
- P0 выше S1–S3 и P1: служебный трафик не блокируется защищённым контуром и пользовательскими правилами.

## 4. Как описано поведение DNS и L3

**DNS-уровень (№18 §5).** В таблицу D-уровней добавлена строка S2/S3 перед D1; D0 трактуется как DNS-реализация S1; D1 и D2 ограничены обычными категориями.

- **DNS Manager обязан блокировать:** системный защищённый список (D0/S1), `Malware` (S2), `Phishing` (S3), пользовательский BLOCK профиля (D3), обычные внешние списки (D2) — кроме устройств в Always DIRECT и устройств с активным `temp_blocklist_off`.
- **Обходятся при Always DIRECT:** только обычные категории (D2 не применяется). `Malware`/`Phishing` не обходятся.
- **Единый порядок DNS и L3 (актуализировано 24.11.2026; исправлено в U7, уточнено в U8):** P0 → D0(S1) → S2 → S3 → **D3/P4 (User BLOCK)** → P1 (Always DIRECT для обычных категорий) → **P3 (модификатор D2)** → **D1/P5 (whitelist)** → **D2/P6 (обычные списки)** → D4/P7–P9 → D5. Метки D0–D5 — идентификаторы, не числовой порядок; отдельной DNS-последовательности нет (№18 §5 п. 0). **P2 (Quick Block) в DNS-порядке отсутствует** — это отдельная UDP-проверка, DNS-ответ она не меняет (№18 §5 п. 0a; уточнено в U8).
- **Whitelist (D1)** снимает только обычную блокировку; на D0/S2/S3 и **D3 (User BLOCK)** не действует — User BLOCK стоит выше whitelist. **`temp_blocklist_off`** отключает только D2-часть и не обходит User BLOCK/S1–S3.
- **Исключение расхождения DNS↔L3:** утверждён единый *результат*, а не механизм (№18 §5 п. 2a–2b). Для угроз оба уровня обязаны блокировать; расхождение — дефект. Для обычных категорий при Always DIRECT оба уровня обязаны пропускать; допустимое расхождение D2/P6 (DNS блокирует, L3 — нет) сохраняется только для устройств `follow` и только пока nft-наборы не включены (REQ-084, meas).

**Кэш DNS и уже установленные соединения (№18 §5 п. 2c).** Утверждённое поведение — конечное состояние; переход к нему не описан. Кэш клиента/роутера и уже установленные соединения могут какое-то время не отражать новое решение. В v1 не обещается мгновенный эффект. Как именно обрабатывать переход (сброс кэша, время жизни, разрыв соединений) — **открытый технический вопрос TQ-01** (см. §8). Механизм не выдуман: он требует отдельного проектного решения и измерения.

## 5. Как исправлен Dry Run

Противоречие №18 §8 (`DIRECT_VIA_LIST` как действующий код) против №19 §6.1 (`OQ-09_PENDING`) устранено: вопрос закрыт, поэтому `OQ-09_PENDING` **отменён**, Dry Run отражает утверждённую модель.

| Код | Когда | Что показывает UI |
|---|---|---|
| `DIRECT_VIA_LIST` | домен в **обычном** списке, устройство в Always DIRECT или активен `temp_blocklist_off` | «Обычная блокировка (реклама/трекеры) не применяется к устройству X» |
| `PROTECTED_BLOCK_KEPT` | устройство в Always DIRECT / домен в whitelist / списки отключены, но домен в `Malware` или `Phishing` | «Остаётся блокировка Malware/Phishing: защищённая категория не отключается» |
| `WHITELIST_OVERRIDE` | whitelist снял **обычную** блокировку | «Разрешён whitelist, источник Y (обычная категория)» |
| `SYSTEM_PROTECTED` | попытка заблокировать системный домен | «Заблокировать нельзя: критический домен» |
| `SHADOWED` / `CONTRADICTION` / `PRECISION_LOW` / `UDP_UNSUPPORTED` | без изменений | как раньше |

Дополнительно Dry Run обязан отдельно показывать, сработал ли S-контур (S1/S2/S3). Коды — спецификация поведения; они не означают, что функциональность уже реализована: реализация не начиналась (это отмечено в №19 §6.1 и в этом документе).

## 8. Какие технические вопросы остались открытыми

1. **TQ-01 — переходный период DNS/соединений.** Кэш DNS (клиента и роутера), уже выданные ответы и установленные соединения при смене режима Always DIRECT или при включении whitelist/`temp_blocklist_off`. Утверждённое конечное поведение задано, переход — нет. Нужны: решение о сбросе кэша, о допустимой задержке и о том, обещается ли разрыв соединений. Не пользовательский вопрос, а проектное решение с измерением.
2. **L3-блокировки обычных списков.** По-прежнему `meas` (REQ-084, W-12): без nft-наборов обычная блокировка остаётся только на DNS. Утверждённое поведение это допускает (результат на L3 — DIRECT), но объём и влияние на RAM не измерены.
3. **Точность привязки DNS↔устройство** (OQ-07, W-14; не W-11) — не изменилась; для Always DIRECT-устройств влияет на то, будет ли DNS-решение вообще отнесено к нужному устройству. **U7:** то же ограничение относится к DNS-части пользовательского BLOCK (D3) — до успешного W-14 она не включается; L3-часть (P4) от W-14 не зависит (№18 §5 п. 1a).
4. **Формулировки UI.** Требование утверждено (№18 §11), точные тексты ещё не согласованы; они не должны утверждать, что защита от рекламы действует на Always DIRECT-устройстве.
5. **Включённость категорий `Malware`/`Phishing` — не определено (U7).** Если категория выключена пользователем, действует ли защита — в решении владельца не оговорено. Документация не объявляет S2/S3 ни безусловно активными, ни зависящими от переключателя: условие «домен в категории» лишь указывает основание срабатывания уровня. Пункт вынесен в №21 §8.1; сценарии №23 26/27/49/53/54 до решения не считаются окончательными. Любая трактовка исполнителя решением не является.

## 10. Какие вопросы требуют отдельного решения пользователя

> **Историческая фиксация на 24.11.2026 (до решений по OQ-01…OQ-13).** Перечисленные ниже OQ-06, OQ-11, OQ-13, OQ-02, OQ-04, OQ-07, OQ-08, OQ-10, OQ-12 позже закрыты решениями владельца; актуальное состояние — №21 §4 и отчёт №31. Раздел сохранён как история интеграции OQ-09/OQ-05.

1. **TQ-01** — как обрабатывать кэш и установленные соединения при смене режима (см. §8). Решение проектное, но влияет на обещания UI.
