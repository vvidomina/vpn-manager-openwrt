## 3. Соответствие таксономий статуса (ТЗ §13 ↔ D-14)

| Ярлык UI (ТЗ §13) | Внутренние состояния |
|---|---|
| normal | `ACTIVE` |
| connecting | `STARTING`, `APPLYING` |
| partial failure | `DEGRADED/*`, `FALLBACK_DIRECT`, `FALLBACK_BLOCK` (вычислено по данным OQ-14, вариант B) |
| critical error | `EMERGENCY_DIRECT`, `DEGRADED/ENGINE_DOWN` без восстановления, `GUARD_*` (вне v1) |
| disabled by user | `DISABLED_BY_USER` |
| maintenance | `MAINTENANCE` |

Правило: **внутренняя модель — единственный источник**; UI-ярлыки вычисляются из неё, обратное преобразование не допускается.

### 4.1.1 Историчность OQ-13: модель заменена U9

Результат OQ-13 в его исходном виде описывает **собственный failover**, которого в U9 нет. Строка OQ-13 сохранена как история решения владельца и не является действующей архитектурой.

Не являются действующими: `server_health`, последовательный failover по приоритету администратора, пороги 2/3 отказа, `last_working_server`, собственное восстановление и «три успешные проверки × 5 минут», проверка серверов раз в минуту / исключённых раз в 5 минут, ping и ручная проверка собственного менеджера как фактор автовыбора, per-device `PROXY_FALLBACK_DIRECT`.

Актуальная замена — штатные механизмы Xray: `observatory` (доступность outbound), `routing.balancers` с четырьмя стратегиями и `fallbackTag` на DIRECT или `blackhole`. Ограничения этой замены были оформлены как OQ-14 и OQ-15 и **закрыты 27.11.2026** вариантами B и A (§4.3, §4.4, отчёт №37); технические проверки по ним остаются [Т]. Действующие требования — REQ-130…REQ-133, REQ-168; модели — №18 §7, №20 §3.

### 4.2 Требования безопасности локального интерфейса (утверждены 27.11.2026)

Относятся к выбранному варианту B и обязательны для реализации:

1. **Только IPv4 loopback.** Адрес слушателя — литерал `127.0.0.1:<порт>`; не `0.0.0.0`, не LAN-адрес, не `localhost` (может разрешиться в `::1`), не `[::1]`, не unix-socket вне доверенного каталога. IPv6-слушателя нет.
2. **Только `ObservatoryService`.** В `api.services` входит одно значение — `ObservatoryService`; `StatsService`, `LoggerService`, `HandlerService`, `RoutingService`, `ReflectionService` не включаются. Другие сервисы — только отдельным решением владельца.
3. **Нет `metrics` и `/debug/vars`.** HTTP-слушатель метрик не создаётся; `metrics`/`debug` в конфигурации отсутствуют.
4. **Нет доступа с LAN/WAN.** Слушатель не открывается в зону `lan`/`wan`, правило firewall не создаётся, системные UCI-зоны не меняются, ACL rpcd на него не распространяется.
5. **Нет нового внешнего API приложения.** gRPC Xray — внутренний локальный канал; собственный сетевой порт демона по-прежнему запрещён (D-05).
6. **Loopback не является аутентификацией.** Привязка к `127.0.0.1` ограничивает сетевой доступ, но не защищает от других локальных процессов с доступом к этому порту. Требуется отдельная проверка UID/GID и фактического доступа на целевом OpenWrt (сценарий 134); до её выполнения безопасность не заявляется доказанной и защита от локальных процессов не обещается.
7. **Минимизация поверхности.** Включается только необходимый gRPC-сервис `ObservatoryService`; другие сервисы не регистрируются. Регистрация сервиса и регистрация отдельных RPC-методов не смешиваются: состав методов определяется включённым сервисом. Ошибка конфигурации сервисов не должна приводить к публикации неподтверждённых полей.
8. **Отказ без деградации границы.** Приложение не переходит на сетевой порт и не создаёт собственную пробу ни при каком отказе наблюдаемости (REQ-168). Ошибка создания listener — это отказ запуска Xray (`DEGRADED/ENGINE_DOWN`, откат по инвариантам жизненного цикла), а не `api_error` при работающем движке. Ошибка вызова API при работающем Xray (`Unimplemented`, таймаут) публикуется как `observability=error` и не выдаётся за отказ VPN. `connection refused` сам по себе не классифицируется: сначала проверяется состояние процесса.

### 4.3 OQ-14: интеграция варианта B (27.11.2026)

**Утверждено владельцем.** Источник данных о состоянии outbound — локальный gRPC `ObservatoryService.GetOutboundStatus`. Listener — только IPv4 loopback `127.0.0.1`; в Xray включается только сервис `ObservatoryService`; `metrics`, `/debug/vars` и отдельный HTTP-listener не используются; доступ из LAN/WAN запрещён; новый внешний HTTP API приложения не создаётся; другие сервисы Xray API — только отдельным решением владельца.

**Подтверждено исходником тега v26.9.9:**

1. Сервис объявлен в `app/observatory/command/command.proto`: `service ObservatoryService { rpc GetOutboundStatus(GetOutboundStatusRequest) returns (GetOutboundStatusResponse) }`; запрос пустой, ответ — `GetOutboundStatusResponse { ObservationResult status = 1 }`.
2. Реализация — `app/observatory/command/command.go`: `GetOutboundStatus` вызывает `s.observatory.GetObservation(ctx)` и возвращает результат без дополнительной фильтрации и без сведений о балансировщике.
3. Конфигурация — `infra/conf/api.go`: `APIConfig` содержит `tag`, `listen`, `services`; имена сервисов сравниваются без учёта регистра. **Неизвестное имя сервиса молча игнорируется** (в `switch` нет ветки `default`), поэтому опечатка не является ошибкой конфигурации.
4. Listener — `app/commander/commander.go`: при непустом `listen` выполняется `net.ResolveTCPAddr("tcp", listen)` и `internet.ListenSystem`; gRPC-сервер поднимается напрямую.
5. Следствие: в минимальной конфигурации **не нужны** dokodemo-door inbound, routing-правило на `api` и outbound `api`. Достаточно одного блока `api` с `listen`.

Минимальная конфигурация:

```json
"api": {
  "tag": "api",
  "listen": "127.0.0.1:<port>",
  "services": ["ObservatoryService"]
}
```

Номер порта — параметр реализации (в документе не назначается): он выбирается из свободного диапазона с проверкой конфликта и с обязательной привязкой только к `127.0.0.1`. Литерал `localhost` не использовать: он может разрешиться в `::1` и создать IPv6-слушатель.

**Поля и поведение `GetOutboundStatus`:**

| Поле `OutboundStatus` | Смысл | Ограничение |
|---|---|---|
| `outbound_tag` | тег outbound | — |
| `alive` | результат последней пробы | не означает «выбран балансировщиком» |
| `delay` | задержка пробы, мс | у мёртвого узла — сентинел `99999999` |
| `last_error_reason` | текст последней ошибки | в proto помечен `NotMachineReadable` — не разбирать |
| `last_seen_time` | время последней успешной пробы, unix | не обновляется при неудаче |
| `last_try_time` | время последней попытки, unix | основание для оценки свежести |
| `health_ping` | `all`, `fail`, `deviation`, `average`, `max`, `min` | заполняется только `burstObservatory`; при обычном `observatory` отсутствует |

Поведение, установленное по `app/observatory/observer.go`:

1. Запись появляется только после первой пробы (`updateStatusForResult`), поэтому **до первого цикла список пуст**. Удалённые из селектора outbound убираются из списка.
2. `GetObservation` стандартного Observer всегда возвращает `nil` в качестве ошибки. Поэтому **пустой список — успешный RPC, а не ошибка**.
3. По API нельзя отличить «цикл ещё не выполнялся» от «`subjectSelector` ни с чем не совпал»: в обоих случаях список пуст. Различие возможно только по сгенерированной конфигурации и логам, поэтому интерпретация помечается как вычисленная.
4. Ошибки вызова API при работающем Xray: `Unimplemented` (сервис не зарегистрирован, например опечатка в `api.services`) и таймаут/`DeadlineExceeded`. Это ошибка наблюдаемости, а не отказ Xray и не отказ VPN. Отдельно: ошибка создания listener (`ResolveTCPAddr`/`ListenSystem`) возвращается из `commander.Start` и прерывает `Instance.Start` — Xray не запускается, поэтому такой случай относится к отказу запуска (`ENGINE_DOWN`), а не к `api_error`. `connection refused` сам по себе не доказывает ни то, ни другое: сначала проверяется процесс.

**Что API не сообщает:** выбранный для потока outbound, состояние балансировщика и факт применения `fallbackTag`. Эти сведения нельзя публиковать как прямое наблюдение.

**Соответствие уровней состояния:**

| Сведение | Источник | Как публиковать |
|---|---|---|
| Статус процесса Xray | procd/ubus, признак S2 | наблюдение |
| Результаты Observatory | `GetOutboundStatus` | наблюдение |
| Доступность outbound | `alive` + `last_try_time` | наблюдение со свежестью |
| Предполагаемое состояние балансировщика | вычисление по `alive` среди outbound подписки | производное, `source=derived` |
| Фактическое использование `fallbackTag` | не сообщается | не публиковать как факт |
| Состояние сервиса | S1–S6 | вычисленное по признакам |

При отсутствии свежих данных публикуется неопределённое состояние («Неизвестно»/`observability=stale`), а не `healthy` или `unavailable`.

### 4.4 OQ-15: интеграция варианта A (27.11.2026)

**Утверждено владельцем:** `leastLoad` остаётся в v1; `burstObservatory` не добавляется; действующий механизм — обычный `observatory`; UI не обещает измерение нагрузки или стабильности; ограничения показываются в UI и диагностике. Подпись — «`leastLoad` — выбор по доступной оценке Xray» с пояснением, что при стандартном Observatory выбор опирается на доступные данные задержки.

**Подтверждено исходником v26.9.9** (`app/router/strategy_leastload.go`, `infra/conf/router_strategy.go`):

1. `HealthPing` берётся из `OutboundStatus`; при обычном `observatory` поле не заполняется, поэтому `RTTDeviation` = `delay`, а `RTTAverage` = `delay`.
2. Сортировка идёт по `RTTDeviationCost` (при обычном Observatory — по задержке), затем по средней задержке, числу отказов/попыток и тегу.
3. `expected` по умолчанию `0` → трактуется как `1`; `baselines` пуст → выбирается `nodes[:1]`, то есть один узел; `maxRTT=0` и `tolerance=0` отключают соответствующие фильтры.
4. При отсутствии пригодных узлов возвращается пустой тег → `fallbackTag`.
5. Следствие: при стандартных параметрах U9 выбор фактически идёт по минимальной задержке. Утверждать полную эквивалентность `leastPing` нельзя: различаются фильтры, порядок обхода и разрешение ничьих.

**Диагностика различает:** стратегия выбрана; результаты Observatory получены; результатов ещё нет; кандидат не найден; применён `fallbackTag` (вычислено); данные устарели; чтение gRPC завершилось ошибкой. Состояния не взаимозаменяемы: «нет данных» ≠ «нет доступных серверов» ≠ «API недоступен».
