### 1.1 Что это значит для ТЗ

1. **Версия OpenWrt зафиксирована: 25.12.6, apk.** Любые упоминания «OpenWrt 25 как ориентир» (ТЗ §2.2) теперь можно заменить фактом. Требование §18 «тип пакета определяется после снятия данных» — выполнено: **APK**, `aarch64_cortex-a53`, `mediatek/filogic`.
2. **iptables нет** — проект обязан быть nftables-only (fw4). Любые legacy-решения недопустимы.
3. **Lua в LuCI недоступен** — §3.2 нужно привести к факту: клиентские JS-вью + ucode на сервере (через `rpcd-mod-ucode`/ubus).
4. **IPv6 у провайдера нет; IPv6-подсистема нужна только внутри.** Обследование 22.11.2026 (документ №8 §1.4): `wan6` не поднялся, глобального адреса/префикса/default route нет, `ip -6 route get 2606:…` → `Network unreachable`; есть только ULA, RA с `lifetime 0` и внутренний IPv6 клиентов. Поэтому утверждение «IPv6 работает» (редакция 1) **опровергнуто**. Решение D-01 с уточнением 22.11.2026: v1 — IPv4-only по внешней маршрутизации; IPv6-подсистема (link-local, ULA, odhcpd, служебные нужды) сохраняется; IPv6-туннелирование и IPv6 TProxy не реализуются; клиентский незаметный IPv6-выход запрещён как цель; механизм ограничения в v1 не реализуется — P-01 «закрыт — вне v1» (ТЗ §5), риск IPv6 bypass принят. В fw4 `accept_to_wan` пропускает любое семейство, а NAT только IPv4, поэтому защита сегодня держится на отсутствии маршрута — латентный риск S1-01.
5. **Состояние движка нельзя выводить из одного файла.** На обследовании 22.11.2026 Xray был остановлен владельцем **вручную** (штатное действие, не отказ), но `/etc/xray/state` остался `mode=vpn`, а `/tmp/xray-state.vol` — `alive=1`. Это подтверждает A-07: старому проекту не хватало состояния «выключено пользователем» и вычисляемого состояния по совокупности признаков (процесс, конфигурация, политика, доступность сервера, проверка трафика). Для нового проекта это требование к архитектуре, а не риск платформы.

## 3. Ограничения платформы и их последствия

### 3.1 RAM (233 МБ, без swap)
В простое свободно ~115 МБ при уже работающем Xray. Бюджет нового стека: демон + Xray + dnsmasq + uhttpd/LuCI. Оценка: Go-демон 15–40 МБ RSS, Xray 40–80 МБ RSS (зависит от числа соединений и буферов), dnsmasq 3–5 МБ, uhttpd+LuCI 5–10 МБ. Итого 65–135 МБ — **влезает, но без большого запаса**.
Опасные режимы: массовое обновление Geo (распаковка/проверка), одновременные health-check'и по всем серверам, большой кэш DNS, много устройств.
Митигации: ограничить число параллельных проб, не держать geo в памяти, ограничить кэш DNS, `GOGC` по умолчанию, отсутствие swap означает, что OOM-killer выбирает жертву сам — демон должен быть устойчив к перезапуску (быстрый старт, восстановление состояния).

### 3.2 Flash (overlay 57.6 МБ, свободно 41.3 МБ)
Факт: `xray-core` + Geo-файлы занимают ~13 МБ overlay (13.2 МБ занято при 68 КБ до установки, `audit:41-47` против `after-zapret:41-47`).
Бюджет нового проекта: Go-демон (статический, `-s -w`: ориентировочно 8–15 МБ), LuCI-вью/ресурсы (<1 МБ), Geo (~0.5 МБ), журналы (ограничить), бэкап (по требованию пользователя, вне overlay при экспорте).
**Риск R-03:** суммарно можно упереться в 41 МБ. Нужно: собрать бинарник без отладочных символов, не тащить cgo, ограничить журналы (кольцо 256 КБ + 1 ротация, D-09), не хранить историю в overlay без лимита. Если места не хватит — вариант «пакет + отдельная установка geo» с проверкой свободного места на этапе install (ТЗ §18 это уже требует).

### 3.3 CPU (2×Cortex-A53) и пропускная способность
Все VPN-операции (REALITY/TLS, маршрутизация Xray) выполняются в userspace на двух ядрах A53. Реальная пропускная способность **не измерялась** и не должна выдумываться (ТЗ §19.3). Ожидаемый порядок величин для такого класса — десятки Мбит/с; точная цифра появится только после измерений.
Дополнительно: `network.globals.packet_steering='0'` [Ф] — распределение сетевой обработки по ядрам отключено; при нагрузке один core может стать бутылочным горлышком. Это параметр, который надо оценить при измерениях.

### 3.4 nftables и fw4
- nft 1.1.6 поддерживает всё нужное: sets с `interval`, `fib`, `tproxy`, `meta mark`, `redirect`, счётчики.
- **iptables отсутствует** — совместимость со старыми гайдами неприменима.
- **flowtable offload включён** (`flags offload`, devices включают `wan`, `lan2-4`, `phy0-ap0`, `phy1-ap0`). Последствия для проекта — см. R-01 в документе №2: правила, рассчитанные на каждый пакет (per-device ограничения, UDP-блокировка), могут не применяться к уже установленным offloaded-потокам. Решение D-12: offload не отключается глобально; сначала A/B-проверка (T-12), затем — при доказанной необходимости — точечное исключение трафика проекта из offload; глобальное отключение только с измерением потери производительности и отдельным согласованием.
- Собственная таблица проекта должна создаваться отдельно от `inet fw4` и не пересекаться с чужими include. На устройстве уже есть висячие include (B-14) — это аргумент за pre-flight-проверку окружения.

### 3.5 Ядро
Нужные модули присутствуют: `kmod-nf-tproxy`, `kmod-nft-tproxy`, `kmod-nft-fib`, `kmod-nf-conntrack`, `kmod-nf-nat`, `kmod-nft-offload`, `kmod-tun` (последний пригодится, если когда-нибудь появится TUN-режим; в первой версии не нужен).
`nf_conntrack_max` = 15360 при 233 МБ RAM — разумный дефолт. Решение D-11: conntrack — только диагностический показатель, предупреждение при > 80 % от текущего значения; не критерий отказа VPN и не фактор failover; sysctl автоматически не меняется.

### 3.6 Пакеты, которых нет и которые нельзя предполагать
`jq`, `python3`, `openssl` (бинарь), `logrotate`, `ss`, `host`. Всё это должно отсутствовать в зависимостях проекта. `curl` есть — но Go-демону он не нужен вовсе.

### 3.7 LuCI
Факт: 26.320, `luci-base`, `luci-mod-*`, `luci-theme-bootstrap`, `ucode-mod-html`, `rpcd-mod-luci`, `rpcd-mod-ucode`. Lua-совместимости нет → **вью на JS (LuCI client-side) + серверные вызовы через ubus/rpcd**. Это соответствует ТЗ §17.2 по духу (браузер не запускает shell), транспорт UI↔демон определён решением D-05 (ubus/rpcd).

Решение D-05: только ubus/rpcd с ACL rpcd; отдельный сетевой HTTP-порт демона не открывается. Проверки прав выполняются на стороне демона, браузер не запускает shell-команды. Собственная модель сессий, TLS и CSRF-токены не нужны — используются штатные механизмы LuCI/rpcd.

### 3.8 Xray на этой платформе
- Версия в feeds: `26.10.21-r1` [Ф]. Схема конфига у 26.x отличается от 1.x (например, `routing.balancers`, `observatory`, `dns` с `servers[].domains`). Проект должен фиксировать поддерживаемую версию и проверять её при старте.
- `xray run -test` доступен и использовался — это ключ к staged apply.
- Опция `sniffing.routeOnly` и `destOverride` поддерживается (использовалась старым кодом) — нужна для доменной маршрутизации при TPROXY.
- Наличие `observatory`/`leastLoad` позволяет делать health-check внутри Xray, но ТЗ требует пользовательский порядок серверов → выбор должен быть в демоне (см. B-06).

## 5. Вопросы безопасности

1. **Секреты в файлах.** Старый проект держал `config.json` и `servers.json` с правами 600 (`audit:343-350`) — правильная практика, сохранить. UCI `xray.subscription.url` хранится в `/etc/config/xray` (права 600 по умолчанию у `/etc/config` — проверить).
2. **Секреты в аргументах процесса.** `xray-update:80-81` передаёт URL подписки в `curl` как аргумент → виден в `ps`. В новом стеке URL передавать только через файл/переменные окружения/HTTP-клиент внутри демона.
3. **Секреты в логах.** `xray-update` логирует только текстовые сообщения (хорошо). Но `xray-monitor`/`xray-watchdog` пишут в `/root/state.log` без маскирования, а `audit.sh` маскирует. В новом стеке маскирование — обязательный слой перед любым выводом (ТЗ §17.1).
4. **Секреты в бэкапе.** D-10: бэкап не шифруется и включает URL/токены подписок и серверы → права 600, предупреждение в UI, исключение Geo/логов/временных файлов/кэша, проверка версии схемы при restore.
5. **LuCI-доступ.** Демон не публикует сетевой HTTP-порт (D-05). Доступ — через ubus/rpcd: ACL rpcd разделяет чтение и изменение, демон повторно валидирует права и аргументы. Операция изменения политики недоступна без соответствующего ACL.
6. **Загрузки из интернета.** Geo-файлы и подписки загружаются из внешней сети; обязательны: проверка формата, ограничение размера, таймауты, отказ от выполнения любых "скриптов" из подписки (в старом проекте это соблюдено — данные разбираются, не исполняются).
7. **Внешние правила из чужих пакетов.** Висячие include (B-14) — пример того, как чужой пакет влияет на firewall проекта. Нужна pre-flight-проверка и отчёт о конфликтах.
8. **Открытые порты.** Старый Xray слушал `:12345` и `:5353` на **всех** интерфейсах (`audit:374-388`), то есть TProxy-порт виден и с WAN, если firewall пропустит. В новом стеке: слушать только loopback/LAN или гарантированно закрывать fw4; проверять это в приёмке.

## 6. Технически сложные места (по возрастанию риска)

1. **Staged apply Xray + nftables без разрыва** — самая сложная часть. Требует: подготовка конфига, `xray -test`, второй listener/порт, переключение правил, проверка e2e, commit/rollback. Ограничение платформы: нет атомарности между nft и процессом; окно отказа неизбежно, важно сделать его нулевым для TCP-потоков или минимальным и заметным.
2. **Единый DNS-менеджер с двумя цепочками на реальном транспорте.** Проблема: dnsmasq — один кэш на всех; разделение «domestic» и «remote» требует либо двух резолверов (Xray DNS + https-dns-proxy/собственный), либо domain-based маршрутизации внутри одного. Проверить на устройстве.
3. **Failover без ложных срабатываний.** Нужны: различение WAN/VPN/DNS, независимые endpoints, гистерезис, защита от одновременного flap. Старый код показал, как это ломается (B-15, B-17).
4. **Per-device политика через nft + TPROXY.** Нужно: определить устройство по MAC (nft `ether saddr`), применить «Always DIRECT» (return из цепочки), учесть IPv6 и offload.
5. **Стабильные ID серверов при обновлении подписки** (B-10) — алгоритм нужно проектировать и тестировать отдельно.
6. **IPv6** — v1 IPv4-only (D-01) плюс страж клиентского выхода и предупреждение; полная поддержка IPv6 — вне v1.
7. **Ресурсы**: 233 МБ RAM, 41 МБ Flash, 2 ядра — все решения проверять на бюджете.

## 8. Итог документа №3

- Платформа **пригодна** для всех ключевых требований ТЗ: nftables+TProxy, policy routing, Xray 26.10, LuCI-вью, apk-пакеты.
- **Ни одно требование ТЗ не признано технически невыполнимым.**
- Ограничения, влияющие на архитектуру: **IPv6 (v1 IPv4-only + страж, D-01)**, **flowtable offload (D-12)**, **Flash 41 МБ**, **RAM без swap**, **2 ядра**, **apk вместо opkg**, **отсутствие Lua в LuCI**, **отсутствие https-dns-proxy на текущей прошивке**.
- Все числовые характеристики производительности **неизвестны** и должны быть получены измерениями; в документах они не выдумываются.
