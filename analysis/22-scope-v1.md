# Документ №22. Объём v1 (U9): обязательное, облегчённое, после измерений, отложенное

Дата: 26.11.2026 (редакция U9).
Основание: решения владельца U9 (26.11.2026); ТЗ v1.0 §1, §18.10; матрица №17; модель №18; состояния №20.
Назначение: однозначно ответить «что входит в первую версию», «что делаем в упрощённом виде», «что нельзя включать до измерений» и «что не делаем». Классификация не меняет утверждённые решения — она определяет порядок и глубину реализации.

Классы: **v1** — обязательно; **lite** — облегчённая реализация с явным ограничением; **meas** — только после измерений/тестового окна; **defer** — отложено (кандидат v2); **out** — не входит в v1 принципиально.

**Изменение относительно U8:** собственные Blocklists (AdBlock, Malware/Phishing, списки, whitelist, DNS-фильтрация, статистика, Quick Block), P4/User BLOCK, P0 как подсистема, System Protected List, DNS Manager, собственный failover/server_health/last_working_server и ручная очистка логов **исключены полностью**, а не отложены. Отложенных «на будущее» заглушек для них нет.

## 1. Обязательное для v1

| Блок | Состав | Требования |
|---|---|---|
| Демон и владение | один Go-демон, procd, единый источник истины; Policy Manager (nft/fwmark/ip rule/route), Xray Manager, Storage, аудит. **DNS Manager и общего журнала событий нет** | REQ-004, 007, 009 |
| API и безопасность | ubus/rpcd без сетевого порта, штатные rpcd ACL, идентичность вызывающего, идемпотентность, оптимистическая блокировка | REQ-006, 014, 103, 111 |
| Конфигурация | JSON, атомарная запись, schema version и миграции, last-good, safe mode | REQ-100 |
| Состояния | D-14 (шесть признаков), `DISABLED_BY_USER`, `FALLBACK_DIRECT`, `FALLBACK_BLOCK`, `WAN_DOWN`, `EMERGENCY_DIRECT`, `MAINTENANCE`, `DEGRADED/*` (без серверных подпричин) | REQ-037–039 |

| Подписки и серверы | одна активная подписка; набор серверов из подписки; атомарная замена непустым ответом; сохранение предыдущего набора при ошибке/пустом ответе; одиночный `vless://` | REQ-020, 021, 023, 026–028, 130–135 |
| Выбор сервера | штатный Xray balancer: `random` (по умолчанию), `roundRobin`, `leastPing`, `leastLoad`; один список стратегии в UI; отдельный ручной override одного сервера | REQ-130, REQ-131, REQ-133 |
| Observatory | `enableConcurrency: true`, `probeInterval: "300s"`, `probeUrl`; `fallbackTag` на DIRECT или `blackhole` | REQ-130–132 |

| Логи | два файла Xray, `logLevel`, 20/50/100 строк, штатный `logrotate` (`daily` + `minsize`, порог 1…50 MB, 5 по умолчанию), одна сжатая копия, `copytruncate` без перезапуска | REQ-137, REQ-160–REQ-163 |
| Dashboard | только критические ошибки Xray-сервиса и наблюдаемость outbound из gRPC `ObservatoryService` (`alive`/`delay`/свежесть; `fallback` — как производное) | REQ-164, REQ-168 |
| Диагностика | эффективная политика и причина, состояния наблюдаемости (`no_data`/`stale`/`api_error`), ограничения `leastLoad`, последние строки логов, экспорт с маскированием | REQ-090, 091, REQ-168 |
| Аудит и Undo | аудит настроек с источником и маскированием; Undo для безопасных изменений | REQ-096, 097 |
| Надёжность | Maintenance Mode, восстановление намерения, штатный procd | REQ-101, 105 |
| Backup | авто перед критическими изменениями, ручной, лимит копий, без шифрования + предупреждение, проверка целостности | REQ-106, 107 |
| Self-update | preflight, backup, проверка после установки, rollback | REQ-108, 109 |
| UI | вкладки без отдельных разделов под удалённые подсистемы; постоянный статус; Saved/Applied/Pending; audit trail; без внешних уведомлений | REQ-099, 120–122 |
| Маршрутизация | модель №18: L1–L4, Always DIRECT, UDP, профили, балансировщик; Dry Run | REQ-022, REQ-154 |

**Принцип v1:** всё перечисленное реализуется без IPv6-политики, без ролей, без внешних интеграций, без собственных менеджеров здоровья/логов/DNS и без обещаний, которые нельзя измерить.

## 2. Облегчённая реализация (lite)

| Функция | Что делаем | Что **не** делаем | Почему | Требование |
|---|---|---|---|---|
| Массовое управление устройствами | Dry Run, перенос в группу, назначение профиля, снятие | нет произвольных «массовых правок всего» | риск необратимых изменений | REQ-066 |
| Undo | только безопасные изменения, с проверкой зависимостей | не «отменяем» сетевые операции задним числом | риск | REQ-097 |
| UDP allowlist | список портов/диапазонов, валидация | нет «умного» определения приложений | не требуется | REQ-151 |
| Ручной override | один сервер, немедленное применение | нет группового закрепления серверов и приоритетных списков | не требуется | REQ-133 |
| Автообновление подписки | переключатель + 6 / 12 / 24 часа | нет расписания в UI и собственного планировщика | штатный `crond` | REQ-134 |

## 3. Требует измерений (meas) — до измерений не включать

| Функция / параметр | Что неизвестно | Проверка | Поведение до измерения |
|---|---|---|---|
| IPv4-таблица, fwmark, nft-priorities | занятость значений, порядок с fw4 | preflight + W-02 | значения предлагаются, не назначаются |
| Offload и per-device политика | обходит ли flowtable правила и счётчики | W-02 | политика проектируется без глобального отключения offload |
| Trial-окно, время старта Xray, бюджет отката | длительности | W-04 | консервативные значения |
| Ручное переключение «без разрыва» | реальный разрыв | W-05 | цель «без разрыва», иначе предупреждение |
| Backup | размер, состав, restore | W-08 | ≤ 1 МБ ориентир |
| Throughput/MTU | реальные числа | W-09 | без обещаний скорости |
| Идентичность rpcd/ACL | фактическое поведение штатных ACL | W-11 (узкая проверка) | контракт, без заявлений о безопасности |
| Интервалы обновления UI | отзывчивость vs нагрузка | W-13 | 2–5 / 5 / 5–10 / 30–60 с |
| Исключение системного трафика роутера | фактическое поведение на AX3000T | read-only аудит в составе W-02…W-09 (отдельное разрешение) | требование согласовано, но не подтверждено |
| Поведение Xray до первых результатов Observatory | холодный старт | W-03 / сценарии 116, 128 | `COLD_START` в диагностике; пустой список API ≠ ошибка; при `leastPing`/`leastLoad` возможен `fallbackTag`, то есть DIRECT при `direct_on_failure=true` (№18 §7.2) |
| gRPC `ObservatoryService` на целевой сборке | версия Xray, фактическая привязка listener, поля ответа | W-03 / сценарии 119–124 | функция не считается подтверждённой; при отсутствии API наблюдаемость = `error` |
| Семантика `leastLoad` на целевой сборке | совпадение с наименьшей задержкой | W-03 / сценарии 126–129 | подпись честная независимо от измерения; `burstObservatory` не добавляется |
| Уже открытые соединения при fallback и восстановлении | переносятся ли | W-03 | не обещается перенос |
| Поддержка UDP сервером | фактическая | W-06 | allowlist не гарантирует туннель |
| `logrotate` в целевой сборке | пакет есть в официальном feed; проверить установку как зависимости, `daily` + `minsize`, `crond`, `copytruncate`, место на flash | W-15 (новая) | функция не считается подтверждённой |

Правило: ни один параметр из этой таблицы не выдаётся за подтверждённый; в №10–№20 они помечены [Т].

**Чего в таблице больше нет:** W-12 (Blocklists) и W-14 (точность DNS↔устройство) удалены из активного плана — соответствующих функций в U9 нет; исторические карточки сохранены в №23 только как история.

## 4. Отложено (defer) — кандидаты v2

| Возможность | Почему отложено | Что нужно для возврата |
|---|---|---|
| **IPv6 Guard и обнаружение глобального IPv6** | ТЗ §5 прямо исключает из v1; тест с имитацией префикса **запрещён** в v1 | отдельная волна требований v2 + свой план тестов |
| IPv6 VPN / TProxy / NAT66 | ТЗ §5 | отдельная волна требований |
| Пересмотр DNS-архитектуры (DoH, Xray native DNS vs `https-dns-proxy`, Google/Cloudflare/Quad9/Yandex, ISP DNS как резерв) | в v1 — только штатный DNS роутера | **неблокирующее напоминание перед выпуском**; отдельное решение владельца |
| Лента событий, Telegram/push, аналитика | решение владельца U9 | отдельное решение + канал доставки |
| Мониторинг RAM/CPU/conntrack, ресурсная панель, авто-лимиты серверов, авто-отключение | решение владельца U9 | отдельное решение |
| Ролевая модель доступа | ТЗ §14: в v1 не нужна | требования к ролям |
| Цифровая подпись пакетов/provenance | ТЗ §14 | инфраструктура подписи |
| Geo-базы как часть backup | ТЗ §14 | размер/лицензия |
| FakeDNS | решение №44 | отдельное решение + совместимость с Xray |
| Автоматическое объединение MAC | запрещено (решение №52) | не планируется |

Аудит настроек и Undo остаются в v1 (REQ-096, REQ-097): это аудит изменений конфигурации, а не лента событий; в `defer` он не переносится.

## 5. Не входит в v1 принципиально (out)

1. **Собственные Blocklists**: AdBlock, списки рекламы/трекеров, Malware/Phishing, загрузка/обновление/дедупликация/валидация списков, whitelist, `temp_blocklist_off`, индивидуальные наборы по устройствам и группам, статистика и история списков, Quick Block.
2. **P4 / User BLOCK** и любая пользовательская блокировка; отдельный аудит существования/управления User BLOCK не проводится.
3. **P0 как подсистема**: собственная маркировка служебного трафика, `SO_MARK`, статические наборы «служебных» адресов, специальная цепочка `output` как функция приложения. Остаётся только требование «собственный трафик роутера не идёт через туннель».
4. **System Protected List** и собственные списки системных доменов/IP/зеркал.
5. **DNS-подсистема**: DNS Manager, Xray DNS как схема v1, DoH/DoT-перехват и блокировка, `https-dns-proxy`, собственный DNS fallback, собственный кеш и его инвалидация, DNS-фильтрация, индивидуальная DNS-атрибуция.
6. **Собственный failover**: `server_priority`, упорядоченный список приоритетов, `server_health`, `last_working_server`, пороги 2/3 отказа, failback «3 × 5 минут», per-device `proxy_fallback`.
7. **Ручная очистка логов** с сохранением N строк, отдельная кнопка удаления логов, перезапуск Xray ради очистки/ротации.
8. **IPv6-политика**, IPv6-фильтры, IPv6-тесты; настройки IPv6 OpenWrt не меняются.
9. **Системные логи OpenWrt**, `logread`, события приложения в UI.
10. Сетевой порт демона, HTTP API, доступ из WAN.
11. Изменение системных UCI-зон `network`/`firewall`; запись в UCI из LuCI.
12. Обещания скорости/задержек без измерений; автоматическое «лечение» сети (очистка conntrack, смена sysctl, убийство служб).
13. Защита от Malware/Phishing и любые обещания DNS-блокировки.
14. **`metrics`, `/debug/vars` и собственный HTTP-интерфейс** чтения состояния Xray не используются (OQ-14, вариант B). Разрешён только локальный gRPC `ObservatoryService` на `127.0.0.1` с единственным сервисом в `api.services`; доступ из LAN/WAN запрещён; собственная проба, собственный health-механизм и собственный сетевой порт демона не создаются. Другие сервисы Xray API — только отдельным решением владельца. Статические проверки блока `api` (`api.tag`, непустой `api.listen`, только IPv4-loopback, запрет unix socket, ровно один сервис, наличие `observatory`) входят в проверки генератора и новых функций не создают.

## 6. Что увидит пользователь в MVP-сценарии

1. Установил пакет → Overview показывает `DISABLED_BY_USER` (VPN не включён сам).
2. Импортировал подписку → список серверов с доступностью из Xray; выбрал стратегию из четырёх; по умолчанию `random`; подписи честные: `leastLoad` — «выбор по доступной оценке Xray».
3. Включил VPN → `STARTING` → проверка трафика → `ACTIVE`; при инфраструктурном сбое — `DEGRADED` с причиной.
4. Все серверы недоступны → Xray уводит VPN-предназначенный трафик в DIRECT (если `direct_on_failure` включён) либо в `blackhole` без выхода в DIRECT. Приложение различает и не смешивает: **ошибку процесса Xray** (S2/S3), **состояние сервиса** (S1–S4, S6), **наблюдение outbound** (`alive`/`delay` из gRPC) и **производное ожидание fallback**. UI показывает предупреждение с пометкой «производное» и не утверждает, что знает фактически выбранный Xray outbound (OQ-14, вариант B).
5. Закрепил один сервер вручную → видно, что активен ручной выбор; при отказе закреплённого сервера срабатывает `fallbackTag` (override реализуется сужением `selector`, №18 §7.4.1); вернул автоматический режим → снова действует стратегия.
6. Включил автообновление подписки → выбрал 6 / 12 / 24 часа; первый плановый запуск — по выбранному интервалу, ручная загрузка доступна всегда; расписание не показывается.
7. Устройство «телевизор» → Always DIRECT: трафик не идёт в туннель, DNS остаётся общим, блокировки нет.
8. UDP-порт вне allowlist → DIRECT (не блокируется); порт в allowlist → в туннель, если сервер поддерживает UDP.
9. Открыл логи → два файла Xray, 20/50/100 строк; ручной очистки нет; объём регулируется порогом и суточной ротацией.
10. Диагностика объясняет: устройство, уровень (Always DIRECT / UDP / правило профиля / балансировщик), правило и причину.
11. Экспортировал backup → предупреждение о секретах; экспортировал диагностику → секреты замаскированы.
