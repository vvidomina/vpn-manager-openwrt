## 4. Минимальная конфигурация `ObservatoryService`

Проверено, что при непустом `api.listen` отдельный inbound, routing-правило и outbound `api` не нужны: `commander` открывает TCP-listener сам.

```json
"api": {
  "tag": "api",
  "listen": "127.0.0.1:<port>",
  "services": ["ObservatoryService"]
}
```

| Свойство | Значение |
|---|---|
| Обязательные поля | `tag` (иначе ошибка «API tag can't be empty»), `listen`, `services` |
| Разрешённый сервис | только `ObservatoryService` |
| Номер порта | параметр реализации; в документации не назначается; выбирается со проверкой конфликта |
| Недопустимые адреса | `0.0.0.0`, LAN-адрес, `localhost` (может дать `::1`), `[::1]` |

**Важное ограничение конфигурации.** Неизвестное имя сервиса в `api.services` **молча игнорируется** (в `APIConfig.Build` нет ветки `default`). Опечатка не является ошибкой конфигурации и не обнаруживается `xray -test`; приложение обязано проверять фактическую доступность метода (например, `Unimplemented` при вызове).

## 5. Требования безопасности loopback

Зафиксированы в №21 §4.2 и REQ-168:

1. Listener только на литерале `127.0.0.1:<port>`; IPv6-слушателя нет.
2. В `api.services` только `ObservatoryService`; `StatsService`, `LoggerService`, `HandlerService`, `RoutingService`, `ReflectionService` не включаются.
3. `metrics`, `/debug/vars` и HTTP-listener отсутствуют.
4. Нет доступа из LAN/WAN; правило firewall для порта не создаётся; системные зоны UCI не меняются.
5. Новый внешний HTTP API приложения не создаётся; запрет сетевого порта демона (D-05) сохраняется.
6. **Loopback не является аутентификацией:** он ограничивает сетевой доступ, но не защищает от других локальных процессов. Требуется проверка UID/GID и фактического доступа на целевом OpenWrt; до неё безопасность не заявляется доказанной.
7. При ошибке listener приложение не переходит на сетевой порт, не создаёт собственную пробу и помечает наблюдаемость как недоступную.

## 6. Поля и ограничения `GetOutboundStatus`

| Поле | Смысл | Ограничение |
|---|---|---|
| `outbound_tag` | тег outbound | — |
| `alive` | результат последней пробы | не означает «выбран балансировщиком» |
| `delay` | задержка пробы, мс | у мёртвого — сентинел `99999999` |
| `last_error_reason` | текст ошибки | в proto `NotMachineReadable`, не разбирать |
| `last_seen_time` | время последней успешной пробы | не обновляется при неудаче |
| `last_try_time` | время последней попытки | основание оценки свежести |
| `health_ping` | `all`, `fail`, `deviation`, `average`, `max`, `min` | при обычном `observatory` отсутствует |

Поведенческие ограничения:

1. До первого цикла список **пуст**; пустой список — успешный RPC, а не ошибка.
2. По API нельзя отличить «цикла ещё не было» от «`subjectSelector` ни с чем не совпал»: в обоих случаях список пуст. Различие — только по конфигурации и логам.
3. Ошибки API транспортные и не равны отказу Xray или VPN.
4. Записи удалённых из селектора outbound исчезают из списка.

## 7. Разделение состояния Observatory и фактического fallback

| Уровень | Что это | Источник | Как публикуется |
|---|---|---|---|
| Модельное состояние | «нет живых outbound → `fallbackTag`» | архитектура и конфигурация | описание |
| Фактическое состояние Xray | выбранный для потока outbound | Xray | **не публикуется**: API не сообщает |
| Наблюдаемое состояние | `alive`, `delay`, `last_try_time`, `last_seen_time` | `GetOutboundStatus` | `servers[]` — наблюдение |
| Вычисленное состояние | «среди outbound подписки нет живых» → ожидается fallback | демон по данным API | `fallback` с `source: "derived"` |
| Опубликованное состояние | `status`, Dashboard | демон | с разделением «наблюдение/производное» |

Правила:

- `fallback` **не** выдаётся за прямое наблюдение; формулировка «Xray применил `fallbackTag`» запрещена.
- Пустой список → `observability=no_data` («результатов ещё нет»), не `unavailable`.
- `observability=error` при ошибке gRPC; статус процесса Xray показывается отдельно.
- При отсутствии свежих данных `alive` не переписывается в `healthy`/`unavailable`.

Диагностические состояния (№20 §7.2): `strategy_selected`, `results_received`, `no_data`, `no_candidate`, `fallback_expected`, `stale`, `api_error` — не взаимозаменяемы.

## 8. Реальное поведение `leastLoad`

Проверено по `app/router/strategy_leastload.go` и `infra/conf/router_strategy.go` тега v26.9.9:

1. `HealthPing` читается из `OutboundStatus`, но заполняется только `burstObservatory`; при обычном `observatory` его нет.
2. Без `HealthPing`: `RTTDeviation = delay`, `RTTAverage = delay`.
3. Сортировка: `RTTDeviationCost` → `RTTAverage` → число отказов → число попыток → тег.
4. `expected=0` → трактуется как `1`; пустые `baselines` → `nodes[:1]`; `maxRTT=0` и `tolerance=0` отключают фильтры.
5. При отсутствии пригодных узлов возвращается пустой тег → `fallbackTag`.
6. Итог при стандартных параметрах U9: выбирается один узел по доступной задержке.

Ограничение формулировки: **полная эквивалентность `leastPing` не утверждается** — различаются фильтры, порядок обхода и разрешение ничьих. Документируется совпадение по существу, а не тождество.

`burstObservatory` в v1 не добавляется; параметры `probeInterval`/`enableConcurrency` не меняются.
