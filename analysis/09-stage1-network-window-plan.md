# Документ №9. Перечень сетевых измерений, ожидающих согласованного окна

**Актуализация U9 (26.11.2026).** Карточка W-14 (точность привязки DNS↔устройство) выведена из активного плана: индивидуальной DNS-атрибуции и Blocklists в U9 нет. W-12 (Blocklists) также не выполняется. Остальные окна сохраняются как исторический план; действующий план — №23.

Дата: 22.11.2026. Составлен по итогам read-only обследования ([`08-stage1-report.md`](08-stage1-report.md)).
Статус: **ни один пункт не запускался.** Все они изменяют сетевое состояние или создают нагрузку и требуют отдельного согласования тестового окна и плана отката.
Рабочий план v1 — **W-02…W-09 и W-10…W-14**. W-01 (клиентский IPv6-выход) в план не входит: ТЗ §5 запрещает IPv6-тестирование в v1.

Общие правила:

1. Окно назначается пользователем (дата/время, длительность); в окне допускается кратковременная деградация доступа, о чём пользователь предупреждается заранее.
2. Перед каждым пунктом — снимок «до» (`nft list ruleset`, `ip rule`, `ip route`, `uci export`, состояние служб) в `/tmp/stage1/<W-xx>/`.
3. Каждый шаг обратим; откат описан в строке «Откат» и выполняется **сразу** при отклонении от критерия.
4. Секреты (URL подписки, UUID, ключи) не попадают в отчёт; вывод маскируется тем же фильтром, что в `stage1/collect.sh`.
5. Пункт считается выполненным только при записи: что сделано, что наблюдалось, статус **пройдено / не пройдено / требует дополнительного теста**.

## W-02. Offload A/B: политика при включённом и отключённом flowtable (T-12)

| Поле | Значение |
|---|---|
| **Цель** | Установить, обходит ли `flowtable ft` правила проекта (per-device, BLOCK/DIRECT/PROXY, UDP) |
| **Метод** | Прогнать одинаковый набор проверок при `flow_offloading=1` и `flow_offloading=0`: обращения с двух клиентов (один в DIRECT, один в PROXY), TCP и UDP, проверка адреса выхода и счётчиков правил. Для отключения — только `uci set firewall.@defaults[0].flow_offloading=0` + `fw4 reload` |
| **Ожидаемое влияние** | Кратковременный разрыв соединений при `fw4 reload` (1–3 с); при отключённом offload — падение throughput, рост CPU |
| **Длительность** | 30 мин |
| **Критерий успеха** | Поведение политики идентично в обоих режимах **или** доказано, что offload обходит конкретное правило (тогда — точечное исключение, D-12); глобальное отключение не остаётся включённым |
| **Откат** | Вернуть `flow_offloading=1` (+ `flow_offloading_hw=1`), `fw4 reload`, сверить `nft list ruleset` с снимком «до» |

## W-03. Три параллельные пробы мониторинга: CPU/RSS/ложные отказы (T-02)

| Поле | Значение |
|---|---|
| **Цель** | Проверить 30 с / 8 с / ≤3 параллельных и различимость «WAN down» vs «сервер down» на реальном железе |
| **Метод** | Синтетический прогон 3 параллельных HTTPS-проб с интервалом 30 с и timeout 8 с в течение 30 мин; измерять `loadavg`, RSS процесса, число таймаутов. Отдельная серия — с искусственным отказом одного аплинка (не затрагивая PPPoE) |
| **Ожидаемое влияние** | Рост CPU/трафика проб; влияния на доступность нет |
| **Длительность** | 30–40 мин |
| **Критерий успеха** | Записаны CPU/RSS; при недоступности одной цели нет массового «все серверы down»; 2 отказа дают `DEGRADED` без переключения, 3 — переключение; отказы основаны на независимых пробах |
| **Откат** | Остановить прогон (свои процессы), следов в конфигурации не остаётся |

## W-04. Trial-окно, время старта Xray и валидация (T-06)

| Поле | Значение |
|---|---|
| **Цель** | Измерить: время `xray -test`, время от запуска Xray до первого успешного запроса через туннель, длительность «мёртвого» окна при рестарте, поведение при ошибке конфига |
| **Метод** | Запустить Xray с текущим валидным конфигом (без TPROXY-правил), затем с TPROXY; контрольный запрос через `health-socks`/прокси; замеры `date +%s` (в busybox нет `%N`). Отдельно — заведомо битый конфиг (`xray -test` должен отказать) |
| **Ожидаемое влияние** | При включении TPROXY — кратковременное изменение пути трафика; при ошибке правил возможен обрыв доступа на десятки секунд |
| **Длительность** | 20–30 мин |
| **Критерий успеха** | Есть числа: время старта, время до первого успешного запроса, длительность окна; при битом конфиге правила не применяются; прежнее состояние восстанавливается |
| **Откат** | Остановить Xray, снять TPROXY-правила, вернуть исходные `nft`/`ip rule` из снимка «до» |

## W-05. Ручное переключение и автовозврат (T-03)

| Поле | Значение |
|---|---|
| **Цель** | Замерить время ручного переключения, поведение при выборе неисправного сервера, работу гистерезиса 3 × 5 мин |
| **Метод** | При работающем старом менеджере: выбрать исправный сервер (замер), затем заведомо неисправный при рабочем текущем (проверить, что текущий сохранён), затем имитировать восстановление предпочтительного и проверить отсутствие «мгновенного» возврата |
| **Ожидаемое влияние** | Возможен кратковременный обрыв трафика при переключении |
| **Длительность** | 25–40 мин (автовозврат — до 15 мин ожидания) |
| **Критерий успеха** | Успех — немедленно; неудача не ломает текущее подключение и показывает ошибку; автовозврат не раньше 3 успехов × 5 мин |
| **Откат** | Вернуть предпочтительный сервер, проверить доступность |

## W-06. Протоколы VLESS+REALITY, VMess, Trojan (T-04)

| Поле | Значение |
|---|---|
| **Цель** | Подтвердить, что все три протокола реально работают на Xray 26.10.21, а неразборчивый/неполный конфиг не выглядит «готовым» |
| **Метод** | Для каждого доступного сервера: генерация конфига, `xray -test`, подключение, целевой запрос, health-check; отдельно — заведомо невалидная ссылка и ссылка с пропущенным обязательным полем |
| **Ожидаемое влияние** | Требует работающего Xray; при неверной конфигурации возможен обрыв трафика |
| **Длительность** | 40–60 мин |
| **Критерий успеха** | Все три протокола проходят трафик; невалидное отвергается; значимые параметры не теряются |
| **Откат** | Вернуть прежний конфиг, `xray -test`, перезапуск, проверка доступа |

## W-07. Кольцевой журнал: объём, ротация, сохранность (T-09)

| Поле | Значение |
|---|---|
| **Цель** | Проверить 256 КБ + 1 ротация, rate limit и сохранность событий после перезагрузки |
| **Метод** | Сначала — на `/tmp` (безопасно): генерация событий с ограничением частоты, ротация, проверка потери строк. Затем — на Flash в отдельном каталоге с последующим удалением. Износ оценить по факту S1-05 (≈50 КБ/сутки при поминутной записи) |
| **Ожидаемое влияние** | Запись в `/tmp` — без влияния; запись на Flash — минимальный износ, каталог удаляется |
| **Длительность** | 15 мин |
| **Критерий успеха** | Ротация работает; важные события переживают перезагрузку; секретов в файле нет; объём не превышает заданный |
| **Откат** | Удалить тестовый каталог и файлы журнала |

## W-08. Backup/restore: состав и размер (T-10)

| Поле | Значение |
|---|---|
| **Цель** | Проверить достаточность состава по D-10 и реальный размер архива без Geo |
| **Метод** | Собрать архив из копии `/etc/xray`, `uci export`, без `geoip.dat`/`geosite.dat`; проверить права, отсутствие логов и временных файлов; восстановление — в отдельный каталог, без активации |
| **Ожидаемое влияние** | Нет (операции в `/tmp`) |
| **Длительность** | 15 мин |
| **Критерий успеха** | Состав соответствует D-10; размер — единицы КБ; права ограничены; невалидная конфигурация не активируется |
| **Откат** | Удалить архив и тестовый каталог |

## W-09. Throughput, MTU и поведение при offload (базовая линия)

| Поле | Значение |
|---|---|
| **Цель** | Получить базовую линию «прямой трафик» и «через Xray», чтобы оценить цену VPN и влияние offload (D-12) |
| **Метод** | `iperf3` на устройстве отсутствует → использовать `curl`/`wget` с известным объёмом или поставить `iperf3` (установка пакета **только** с отдельным разрешением). Замер: DIRECT, затем PROXY, затем при отключённом offload. Отдельно — проверка PMTU (MTU PPPoE 1492) |
| **Ожидаемое влияние** | Нагрузка на канал и CPU в пределах окна |
| **Длительность** | 30 мин |
| **Критерий успеха** | Три числа (DIRECT / PROXY / без offload) получены в одинаковых условиях; вывод о необходимости точечного исключения обоснован |
| **Откат** | Вернуть настройки offload; удалить временные файлы |

## Что для этих пунктов нужно от пользователя

1. Согласовать окно: дата/время начала и допустимая длительность (рекомендуется 60–90 мин подряд для W-02, W-04…W-06).
2. Подтвердить, что кратковременная деградация доступа в окне допустима.
3. Отдельно решить: разрешена ли установка `iperf3` (W-09).

В v1 не выполняется ни одно IPv6-измерение: W-01 исключён из плана и в тестовые окна не включается (ТЗ §5).
4. Указать, есть ли доступный сервер для каждого протокола (W-06) — иначе пункт помечается «невозможно проверить».

До согласования окна эти измерения не запускаются; новых изменений в системе не производится.

## Архив. Карточка W-01 (клиентский IPv6-выход) — задел v2

> **Не является планом работ v1. Запрещено выполнять в v1. Не включать в тестовые окна и не запрашивать разрешение на выполнение.**

Карточка сохранена только как история замысла для возможного возврата темы в v2. Она приведена без исполняемых команд, без критериев выполнения и без методики имитации глобального префикса: ни выполнять, ни воспроизводить её в v1 нельзя — включая read-only замеры.

| Поле | Историческое содержание (только v2) |
|---|---|
| Что предполагалось выяснить | есть ли у LAN-клиента внешний IPv6-выход при отсутствии IPv6 у провайдера и как ведёт себя политика при появлении глобального IPv6 |
| Почему не выполняется в v1 | ТЗ §5 прямо запрещает IPv6-тестирование в v1; риск IPv6 bypass принят пользователем (C3-01, R3-01) |
| Условие возврата | отдельная волна требований v2: собственный план тестов, критерии, влияние, откат и новое согласование владельца |
