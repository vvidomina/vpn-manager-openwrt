## 1. Ядро демона (Core / Supervisor)

**Ответственность и границы.** Жизненный цикл демона, регистрация модулей, очередь операций изменения, единый mutex сети, внутренняя шина событий, вычисление состояния VPN по шести признакам (D-14). Не выполняет системных изменений сам — только координирует.

**Входы.** ubus-вызовы от API; события модулей (процесс, здоровье сервера, политика, WAN); сигналы procd.
**Выходы.** Команды модулям; публичные события `state.changed`, `op.progress`; runtime-снимок для статуса.

**Публичные методы и события.**
- `vpn.enable`, `vpn.disable`, `vpn.status` (делегируются в API).
- Внутренние: `Submit(op) (opID, error)`, `State() Snapshot`, `Subscribe(topic) <-chan Event`.
- События: `state.changed`, `intent.changed`, `op.started/finished/failed`, `recovery.started/finished`.

**Состояния и ошибки.** Состояния системы — из §5 документа №10 (11 значений). Ошибки: `VM_ERR_BUSY` (идёт другая операция), `VM_ERR_INVALID_STATE` (операция невозможна в текущем состоянии), `VM_ERR_TIMEOUT`, `VM_ERR_INTERNAL`.

**Взаимодействие.** Вызывает Transaction Manager для любых изменений; получает доступность от Xray Observatory и не хранит её; отдаёт снимок API и Diagnostics.

**Владение.** Очередь операций, mutex, runtime-состояние в `/tmp/vpnmanager`. Не владеет ни одним системным сетевым ресурсом.

**Безопасность.** Не принимает команд из сети; все входы — типизированные структуры; инициатор операции фиксируется (ubus-сессия/uid).

**Поведение при отказах.** Паника модуля перехватывается и превращается в `DEGRADED` с событием; при потере связи с модулем состояние не «залипает» — признаки стареют и дают `UNKNOWN`. Перезапуск демона не оставляет систему в промежуточном состоянии: recovery выполняется до публикации `ACTIVE`.

**Критерии приёмки.**
1. Состояние вычисляется только по шести признакам; удаление любого файла состояния не делает систему `ACTIVE`.
2. Параллельный второй запрос изменения получает `BUSY`, сеть не меняется дважды.
3. При `intent=disabled` ни один компонент не запускает recovery.
4. Событие `state.changed` содержит причину и признаки, по которым оно вычислено.

## 2. ubus/rpcd API и ACL

**Ответственность и границы.** Единственный канал UI ↔ демон (D-05). Валидация схем, проверка прав, идемпотентность, длительные операции через `op_id`. Не содержит бизнес-логики.

**Входы.** ubus-запросы LuCI/CLI; rpcd-сессия и ACL.
**Выходы.** JSON-ответы по схемам (§12); события `vpnmanager.event`.

**Публичные методы и события.** Объекты: `vpnmanager` (status/enable/disable), `vpnmanager.config`, `vpnmanager.servers`, `vpnmanager.subscriptions`, `vpnmanager.profiles`, `vpnmanager.devices`, `vpnmanager.dns`, `vpnmanager.policy`, ~~`vpnmanager.ipv6`~~ (reserved, v2), `vpnmanager.diagnostics`, `vpnmanager.backup`, `vpnmanager.operation`. Полный перечень — документ №12 §3.
События: `state`, `config`, `servers`, `devices`, `dns`, `operation`, `log` (`ipv6` — reserved, v2).

**Состояния и ошибки.** Коды `VM_OK`, `VM_ERR_INVALID_ARGUMENT`, `VM_ERR_NOT_FOUND`, `VM_ERR_CONFLICT`, `VM_ERR_BUSY`, `VM_ERR_FORBIDDEN`, `VM_ERR_UNSUPPORTED`, `VM_ERR_TIMEOUT`, `VM_ERR_INTERNAL`, `VM_ERR_STORAGE`, `VM_ERR_VALIDATION`, `VM_ERR_ROLLED_BACK`.

**Взаимодействие.** rpcd → ACL → объект → Core. Демон повторно проверяет права (не доверяет ACL как единственной защите).

**Владение.** ubus-объекты и `acl.d/vpnmanager.json`. Сетевых портов не открывает.

**Безопасность.** Минимальные права: чтение статуса — отдельно от изменения; диагностика — отдельно; backup/restore и очистка — отдельно. Никаких «выполнить команду» методов. Ограничение размера запроса и глубины JSON.

**Поведение при отказах.** Недоступный демон → внятная ошибка UI, без подвисания; таймаут длительной операции не отменяет её молча — возвращается `op_id` и состояние.

**Критерии приёмки.**
1. Браузер с read-ACL не может вызвать изменяющий метод (T-05).
2. Нет метода, принимающего произвольную shell-команду или путь.
3. Длительные операции возвращают `op_id`; статус доступен и после переподключения UI.
4. Ошибки различаются по коду, а не по тексту.

## 3. Policy Manager

**Ответственность и границы.** Единственный владелец nftables-таблицы проекта, fwmark, `ip rule` и таблицы маршрутизации; применение/снятие перехвата, per-device правила. IPv6-цепочек в v1 нет (ТЗ §5). Не решает, *какой* сервер выбрать, и не пишет конфиг Xray.

**Входы.** Желаемая политика от Transaction Manager: набор правил (LAN→proxy, DIRECT-устройства, UDP allowlist), порт TPROXY, mark, таблица.
**Выходы.** Применённое состояние правил; счётчики; событие `policy.applied/failed`.

**Публичные методы и события.**
```go
type Policy interface {
    Stage(ctx context.Context, p Desired) (Plan, error) // nft -c, без изменений
    Apply(ctx context.Context, plan Plan) (Applied, error)
    Rollback(ctx context.Context, prev Applied) error
    Remove(ctx context.Context) error
    Status(ctx context.Context) (Status, error) // наличие, счётчики, расхождения
}
```
События: `policy.applied`, `policy.removed`, `policy.mismatch`, `policy.apply_failed`.

**Состояния и ошибки.** `absent`, `staged`, `applied`, `mismatch`, `failed`. Ошибки: `VM_ERR_NFT`, `VM_ERR_ROUTE`, `VM_ERR_RULE`, `VM_ERR_MARK_BUSY`, `VM_ERR_TABLE_BUSY`.

**Взаимодействие.** Вызывается только Transaction Manager; читается Diagnostics; сообщает Core о расхождении.

**Владение.** `table inet vpnmanager` (только IPv4-цепочки), `ip rule` с проектным mark, таблица 1000 (номер — [П], проверить занятость; 100 занята `zeroblock`). `/etc/config/firewall` **не меняет**.

**Безопасность.** Только атомарные nft-транзакции; все имена интерфейсов/адресов валидируются; запрещена интерполяция пользовательских строк в правила.

**Поведение при отказах.** При ошибке применения — восстановление предыдущего снимка; при невозможности — снятие перехвата (DIRECT) и `DEGRADED/POLICY_NOT_APPLIED`; правила на неработающий порт не остаются никогда (B-05). При перезагрузке «осиротевшие» правила удаляются по метке таблицы.

**Критерии приёмки.**
1. Повторное применение идемпотентно: нет дублей цепочек/правил/route.
2. Искусственная ошибка nft → система в DIRECT, без «полуприменённых» правил.
3. Нет состояния «правило указывает на закрытый порт».
4. Расхождение (правило удалено извне) обнаруживается и отражается в статусе.
5. В v1 IPv6-правил нет; порядок IPv4-правил относительно fw4 и поведение при offload — [Т] до W-02.

## 4. DNS — выведен из состава компонентов (**superseded U9**)

**Статус: компонент не реализуется.** В U9 DNS — штатный DNS роутера/OpenWrt для всех устройств, включая Always DIRECT.

Контракт DNS Manager (цепочки DoH/ISP/Remote, собственный DoH-клиент, bootstrap, переключение upstream, форма ответа при блокировке, состояние fallback, `dns.*` события) **не действует**. Не создаются: DNS Manager, собственный DNS fallback, `https-dns-proxy` как схема v1, Xray DNS как действующая схема, отдельный DNS-кеш и его инвалидация, DNS-фильтрация, индивидуальная DNS-атрибуция.

**Что остаётся:** приложение не перехватывает и не переопределяет DNS; не меняет DNS-ответ; не ведёт DNS-состояний. Напоминание пересмотреть DNS-архитектуру перед выпуском — неблокирующее (№22 §4). Методы `vpnmanager.dns.*` в API U9 отсутствуют (№12).

**Критерии:** в конфигурации Xray и приложения нет DNS- TProxy/перехвата; в UI нет DNS-настроек проекта; смена профиля или подписки не меняет DNS.

## 5. Xray Manager

**Ответственность и границы.** Генерация конфига Xray, валидация `xray -test`, запуск/остановка/перезапуск процесса, проверка слушателей, preflight outbound, trial-проверка реального трафика, переключение сервера без «мёртвого порта». Не владеет nft/route и не решает, когда включать VPN (это Core/Transaction).

**Входы.** Сервер + профиль + режим (proxy/direct), политика UDP, порт TPROXY, состояние DNS (Guard — вне v1).
**Выходы.** Файл конфига, PID/состояние процесса, результат валидации и проб, событие `xray.*`.

**Публичные методы и события.**
```go
type Xray interface {
    Build(ctx, Selection) (Artifact, error)   // конфиг в /tmp, хэш
    Validate(ctx, Artifact) error             // xray -test
    Preflight(ctx, Artifact) (Probe, error)   // проверка outbound без политики
    Start(ctx, Artifact) (Instance, error)
    Stop(ctx) error
    VerifyTraffic(ctx) (TrafficProof, error)  // запрос именно через туннель
    Switch(ctx, Artifact) error               // без разрыва, если возможно
}
```
События: `xray.started`, `xray.stopped`, `xray.exited`, `xray.validation_failed`, `xray.traffic_verified`, `xray.traffic_failed`.

**Состояния и ошибки.** `absent`, `starting`, `running`, `listening`, `verifying`, `stopping`, `crashed`. Ошибки: `VM_ERR_XRAY_CONFIG`, `VM_ERR_XRAY_START`, `VM_ERR_XRAY_LISTEN`, `VM_ERR_XRAY_PROBE`, `VM_ERR_XRAY_TRAFFIC`.

**Взаимодействие.** Transaction Manager — этапы; Policy Manager — порт/перехват; Failover — пробы; DNS — Remote DNS; Subscription/Profile — данные.

**Владение.** `/etc/xray/config.json` (единственный писатель), процесс Xray, временные артефакты в `/tmp/vpnmanager`. Слушатели: TPROXY на `br-lan`/loopback, health/probe — только loopback (S1-09).

**Безопасность.** Секреты (UUID/ключи) не попадают в логи и API; файл 0600; конфиг не содержит лишних inbound на `0.0.0.0`; проверка, что сгенерированный конфиг соответствует версии генератора (хэш).

**Поведение при отказах.** Ошибка валидации — apply не начинается; процесс упал — политика снимается (нет трафика в мёртвый порт), затем backoff-рестарт; traffic proof не получен — откат; повторные падения — `EMERGENCY_DIRECT` с событием.

**Критерии приёмки.**
1. `xray -test` обязателен перед каждым применением (T-06).
2. Успешный запуск процесса сам по себе не даёт `ACTIVE` — нужен traffic proof (D-06).
3. Ни в одном сценарии нет правил, указывающих на неработающий порт.
4. Переключение не рвёт текущее соединение при доступном новом сервере (или разрыв ограничен и измерен — [Т] W-05).
5. Конфиг воспроизводим: одинаковый вход → одинаковый хэш.

## 6. IPv6 Guard — **архив v2** (в v1 не реализуется)

> **Статус на 22.11.2026.** ТЗ v1.0 §5 (решение №11) исключает IPv6 Guard, детект глобального IPv6 и любые IPv6-правила из первой версии; риск принят (решение №14). Контракт ниже **не реализуется в v1** и сохранён как задел v2. Компонент в v1 не существует: нет объекта, нет событий, нет ACL. Обоснование — №15 §3.2, №21 C3-01.

**Ответственность и границы (v2-задел).** Обнаружение глобального IPv6 на WAN и обеспечение запрета клиентского IPv6-форварда. Не отключает IPv6-подсистему, не настраивает RA/DHCPv6, не трогает `network`/`firewall` UCI, не делает NAT66.

**Входы.** `ubus network.interface` (`wan`, `wan6`), `ip -6 addr`, `ip -6 route`, префиксы odhcpd, состояние правила в nft.
**Выходы.** `ipv6_wan_present`, источники (адрес/префикс/маршрут), `guard_installed`, `client_ipv6_egress`, счётчик, событие.

**Публичные методы.**
```go
type Guard interface {
    Detect(ctx) (Detection, error)
    Ensure(ctx, Policy) error   // идемпотентно ставит/снимает правило через Policy Manager
    Status(ctx) (Status, error)
}
```
События (только задел v2; в v1 не публикуются): `ipv6.present`, `ipv6.absent`, `ipv6.guard_failed`, `ipv6.guard_restored`.

**Состояния и ошибки (задел v2).** `ABSENT`, `PRESENT_GUARDED`, `PRESENT_UNGUARDED`, `GUARD_UNKNOWN`. В v1 этих состояний и связанных предупреждений в UI нет (REQ-011, ТЗ §5): обязательного предупреждения об ограничениях IPv6 в v1 не существует. Ошибки: `VM_ERR_GUARD_APPLY`, `VM_ERR_GUARD_VERIFY`.

**Взаимодействие.** Policy Manager — установка правила; Core — состояние и предупреждение; Diagnostics — отчёт.

**Владение.** Только цепочка `ipv6_guard` (через Policy Manager). Конфигурация IPv6/RA/DHCPv6 — **не его**.

**Безопасность.** Не меняет адресацию и не отключает IPv6; правило не затрагивает LAN→LAN и трафик самого роутера; ошибка установки не маскируется.

**Поведение при отказах.** Не удалось поставить правило → `GUARD_UNKNOWN` + критическое предупреждение, повтор с backoff; не удалось проверить наличие IPv6 → не считать «отсутствует» доказанным; при исчезновении IPv6 правило может оставаться (безвредно) — решение [П].

**Критерии приёмки.**
1. При появлении глобального адреса/префикса клиент не получает IPv6-выход (критерий задела v2; в v1 W-01 и любые IPv6-тесты запрещены).
2. Внутренний IPv6 LAN и служебный IPv6 роутера работают.
3. Отсутствие default route не считается защитой: состояние отражает именно наличие/отсутствие правила.
4. При сбое правила UI показывает критическое предупреждение, а не «всё хорошо».

## 7. Device Manager

**Ответственность и границы.** Обнаружение устройств (DHCP leases, neigh/ARP, Wi-Fi association, bridge FDB), устойчивая идентичность по MAC, offline-записи, объединение записей, назначение Always DIRECT. Не применяет правила сам — отдаёт назначения Policy Manager.

**Входы.** `/tmp/dhcp.leases`, `ip neigh`, `iwinfo`/ubus `hostapd`, `bridge fdb`; ручные назначения.
**Выходы.** Список устройств (MAC, IP, hostname, online, last_seen, источник), карта «устройство → режим», событие `devices.changed`.

**Публичные методы.**
```go
type Devices interface {
    List(ctx, Filter) ([]Device, error)
    SetMode(ctx, mac string, mode Mode) error // default|always_direct
    Merge(ctx, macs []string) error
    Resolve(ctx) ([]Assignment, error)
}
```
События: `device.online`, `device.offline`, `device.added`, `device.merged`, `device.mode_changed`.

**Состояния и ошибки.** `online`, `offline`, `unknown`, `merged`. Ошибки: `VM_ERR_DEVICE_NOT_FOUND`, `VM_ERR_MAC_INVALID`, `VM_ERR_DEVICE_LIMIT`.

**Взаимодействие.** Policy Manager — per-device правила; Core — события; Storage — offline-записи; Diagnostics — отчёт о MAC-рандомизации.

**Владение.** Модель устройств в `/etc/vpnmanager/devices.json`; источник истины по MAC — только этот модуль.

**Безопасность.** MAC валидируется; имена не интерпретируются как код/команды; данные устройств не уходят наружу; лимит записей.

**Поведение при отказах.** Пропал источник (например, `iwinfo`) — используются остальные, устройство помечается `unknown`, а не удаляется; offline-записи сохраняются с TTL ([П]); при переполнении — отказ с понятной ошибкой, без молчаливого удаления.

**Критерии приёмки.**
1. Устройство с Always DIRECT обходит правила DIRECT/PROXY профиля, UDP allowlist и VPN-балансировщик; трафик не блокируется, DNS остаётся штатным DNS роутера (U9). Блокирующих уровней, Quick Block и пользовательского BLOCK в U9 нет; проверка — сценарии №71–№76 (№23 §9). При включении режима UI показывает, что трафик устройства не идёт в туннель, и краткое постоянное пояснение в карточке.
2. Перезагрузка не теряет назначения.
3. MAC-рандомизация не создаёт бесконечный рост записей (лимит/TTL — [П]).
4. Объединение записей не ломает назначения.

## 8. Subscription Manager

**Ответственность и границы.** Загрузка подписок (URL/файл), разбор форматов, извлечение серверов, ID текущего набора, транзакционное обновление, отчёт импорта, сохранение override по точному совпадению нормализованной конфигурации (№13 §3.1). Не решает, какой сервер активен, и не назначает профили.

**Входы.** URL (с токеном), локальный файл, ответ провайдера (JSON/Base64/список ссылок), пользовательский порядок.
**Выходы.** Подписки, серверы, отчёт «принято N / отклонено M / причины», событие.

**Публичные методы.**
```go
type Subscriptions interface {
    Add(ctx, Source) (Subscription, error)
    Update(ctx, id string) (Report, error)
    Remove(ctx, id string) error
    Reorder(ctx, ids []string) error
    List(ctx) ([]Subscription, error)
}
```
События: `subscription.updated`, `subscription.failed`, `subscription.import_report`.

**Состояния и ошибки.** `never_updated`, `updating`, `ok`, `stale`, `failed`, `restricted`. Ошибки: `VM_ERR_FETCH`, `VM_ERR_PARSE`, `VM_ERR_EMPTY`, `VM_ERR_LIMIT`, `VM_ERR_SCHEMA`.

**Взаимодействие.** Profile Manager — Restricted-признак; Xray Observatory — доступность (приложение её не хранит); Storage — данные; Core — событие обновления.

**Владение.** `subscriptions.json`, `servers.json`; URL/токены — только здесь.

**Безопасность.** HTTPS с проверкой сертификата; токен маскируется в API/логах; ограничение размера ответа и времени; запрет редиректов на небезопасные схемы; SSRF-защита (не обращаться к localhost/метаданным).

**Поведение при отказах.** Неудачное обновление не стирает прежние серверы; частичный разбор сохраняет валидные и отдаёт отчёт; пустой ответ — `VM_ERR_EMPTY`, а не «удалить всё»; одновременное обновление и ручная правка сериализуются.

**Критерии приёмки.**
1. Неудачное обновление не ухудшает текущее подключение.
2. Отчёт импорта показывает отклонённые записи и причины.
3. ID текущего набора не меняется при переупорядочивании и косметических правках.
4. Токен не виден в логах/диагностике/UI после сохранения.
5. Пользовательский порядок сохраняется после обновления (D-13).

## 9. Profile Manager

**Ответственность и границы.** Хранение профилей (routeOrder, 6 списков, DomainStrategy, GlobalProxy, UDP), компиляция правил в детерминированном порядке, признак Restricted, Pending reconnect. Не генерирует конфиг Xray напрямую — отдаёт компилятору Xray Manager.

**Входы.** Профиль провайдера/пользователя, приоритеты, назначения, тип подписки.
**Выходы.** Скомпилированный набор правил, состояние профиля, событие.

**Публичные методы.**
```go
type Profiles interface {
    Save(ctx, Profile) error
    Assign(ctx, serverID, profileID string) error
    Compile(ctx, Profile) (Ruleset, error)
    SetPending(ctx, profileID string) error
    List(ctx) ([]Profile, error)
}
```
События: `profile.saved`, `profile.compiled`, `profile.pending`, `profile.invalid`.

**Состояния и ошибки.** `draft`, `saved`, `applied`, `pending_reconnect`, `invalid`. Ошибки: `VM_ERR_PROFILE_SCHEMA`, `VM_ERR_ROUTE_ORDER`, `VM_ERR_RESTRICTED`.

**Взаимодействие.** Subscription Manager — источник; Xray Manager — правила; Core — Pending reconnect; UI — редактирование.

**Владение.** `profiles.json`, `assignments.json`.

**Безопасность.** Валидация доменов/списков; запрет пустых/циклических правил; Restricted не обходится назначением профиля (D-07/D-13).

**Поведение при отказах.** Невалидный профиль не применяется и не заменяет рабочий; Pending reconnect сохраняется до следующего переподключения и не теряется при сбое.

**Критерии приёмки.**
1. routeOrder соблюдается (B-01).
2. GlobalProxy соблюдается (B-02).
3. Restricted запрещает назначение профиля, но не блокирует переключение подписки (D-13).
4. Компиляция детерминирована: одинаковый профиль → одинаковый ruleset.

## 10. Доступность серверов — **выведена из состава компонентов (superseded U9)**

**Статус: собственный Failover Manager не реализуется.** Выбор сервера и проверки доступности выполняет штатный Xray: `observatory`, `routing.balancers` (четыре стратегии), `fallbackTag`.

**Что удалено:** health-check приложения (30 с / 8 с / ≤3), счётчики отказов, переходы `server_health`, `Select`/`RequireSwitch`, `last_working_server`, приоритетный список серверов, автовозврат «3 × 5 минут», per-device fallback.

**Что остаётся у приложения:**
1. Генерация конфигурации Observatory и balancer с корректными `subjectSelector`, `probeUrl`, `probeInterval`, `enableConcurrency`.
2. `fallbackTag` по значению `direct_on_failure`.
3. Ручной override одного сервера: закрепление, ограничение балансировщика; при успешном обновлении сохраняется, если выбранный сервер остался в наборе (точное совпадение нормализованной конфигурации), иначе сбрасывается в `auto`.
4. Отображение того, что сообщает Xray, без собственной интерпретации «здоров/не здоров» и без обещания мгновенного обнаружения отказа.
5. Классификация `WAN_DOWN` отдельно от недоступности серверов.

**Критерии:** в коде нет собственного здоровья серверов и счётчиков отказов; при недоступности всех серверов поведение определяется `fallbackTag`; UI не утверждает, что ping влияет на выбор вне стратегии `leastPing`.

## 11. Staged Apply и rollback (Transaction Manager)

**Ответственность и границы.** Проведение транзакции «конфигурация + политика + процесс» по фазам P0–P8 (документ №10 §7), журнал фаз, last-good snapshot, восстановление после сбоя и перезагрузки, защита от циклов. Не генерирует конфиг и не пишет правила сам.

**Входы.** Запрос apply/switch/restore с ревизией конфигурации; текущий last-good; снимки предыдущих правил.
**Выходы.** `op_id`, результат (applied/rolled_back/failed), журнал фаз, новое состояние.

**Публичные методы и события.**
```go
type Transactions interface {
    Begin(ctx, Request) (Operation, error)
    Status(ctx, opID string) (Operation, error)
    Rollback(ctx, opID string, reason string) error
    Recover(ctx) (RecoveryReport, error)
}
```
События: `tx.started`, `tx.phase`, `tx.committed`, `tx.rolled_back`, `tx.recovered`.

**Состояния и ошибки.** `preparing`, `validating`, `staging`, `starting`, `applying`, `trial`, `committed`, `rolling_back`, `rolled_back`, `failed`. Ошибки: `VM_ERR_BUSY`, `VM_ERR_PREFLIGHT`, `VM_ERR_TRIAL`, `VM_ERR_ROLLBACK_FAILED`.

**Взаимодействие.** Xray Manager, Policy Manager, Storage, аудит; вызывается только Core.

**Владение.** Журнал транзакций и last-good snapshot; блокировка сети на время транзакции.

**Безопасность.** Инициатор и причина фиксируются; откат не требует секретов; восстановление не выполняет пользовательский ввод.

**Поведение при отказах.** Сбой любой фазы → откат к last-good; если откат невозможен → аварийный DIRECT (`EMERGENCY_DIRECT`), интернет сохраняется, причина видима. Перезагрузка посреди транзакции → незавершённая транзакция отбрасывается, выполняется recovery.

**Критерии приёмки.**
1. Новая конфигурация не становится постоянной до успешного trial (D-06, T-06).
2. Прежняя рабочая конфигурация восстанавливается при любом искусственном сбое.
3. После перезагрузки нет «полуприменённого» состояния и осиротевших правил.
4. Ограничение циклов apply/rollback соблюдается.

## 12. Backup, logging и diagnostics

**Ответственность и границы.** Три отдельных сервиса в одном модуле:
- **Backup** — создание/восстановление копии по D-10, версия схемы, валидация restore.
- **Логи** — только два Xray-лога (`access.log`, `error.log`), просмотр 20/50/100 строк, штатный `logrotate` (`daily` + `minsize`, `copytruncate`). Собственного журнала событий и ручной очистки нет.
- **Diagnostics** — read-only отчёты: состояние, правила, слушатели, WAN, конфликты; мониторинга ресурсов и conntrack нет. IPv6 в действующую диагностику v1 **не входит**: наличие глобального IPv6 не обнаруживается, не вычисляется и не отображается (ТЗ §5, решение №11). Контракт стража — §6, помечен как архив v2.

**Входы.** События модулей, запрос backup/restore, запрос отчёта.
**Выходы.** Архив, журналы, отчёт (текст/JSON), событие.

**Публичные методы и события.**
```go
type Ops interface {
    Backup(ctx, Options) (Archive, error)
    Restore(ctx, Archive, Confirm) error
    Report(ctx, Kind) (Report, error)
    ListLogs(ctx) ([]LogFile, error)
}
```
События: `backup.created`, `backup.restored`, `logrotate.completed`, `logrotate.failed`, `diagnostics.ready`.

**Состояния и ошибки.** `idle`, `running`, `done`, `failed`, `incompatible`. Ошибки: `VM_ERR_STORAGE`, `VM_ERR_BACKUP_SCHEMA`, `VM_ERR_NO_SPACE`, `VM_ERR_RESTORE_VALIDATION`.

**Взаимодействие.** Storage — файлы; Core — события; UI — отчёты; Transaction — restore через apply.

**Владение.** `/etc/vpnmanager/backup/*`, конфигурация `logrotate`, отчёты в `/tmp`.

**Безопасность.** Маскирование URL/токенов/UUID/ключей; архив без шифрования (D-10), права 0600, предупреждение; диагностика не выполняет изменяющих команд.

**Поведение при отказах.** Нет места — backup отклоняется до записи; повреждённый архив — restore отклоняется с причиной; ротация не повреждает исходный лог и не останавливает Xray; потеря части записей в окне `copytruncate` не отрицается.

**Критерии приёмки.**
1. Секретов в логах и отчётах нет (T-09).
2. Ротация не повреждает логи и не перезапускает Xray; на файл не более одной сжатой копии.
3. Restore не активирует невалидную конфигурацию (T-10).
4. Состав backup соответствует D-10, Geo/логи/время исключены.
5. Диагностика работает при `DEGRADED` и не меняет состояние.

## 13. LuCI UI и взаимодействие с daemon API

**Ответственность и границы.** Отображение состояния и управление через ubus; никакой бизнес-логики и никаких прямых системных вызовов. Lua-контроллеры не используются (их нет на прошивке) — JS-вью + ucode/rpcd.

**Входы.** События `vpnmanager.event`, ответы методов, действия пользователя.
**Выходы.** ubus-вызовы; отображение статуса, предупреждений, отчётов.

**Экраны (минимум, ровно шесть вкладок).** Overview; Subscriptions & Servers; Devices; Routing; Diagnostics; System (включая intent).

**Публичные методы и события.** Только через `vpnmanager.*`; подписка на события вместо частого опроса.

**Состояния и ошибки.** Отображает все состояния системы и причины `DEGRADED`; ошибки API — человекочитаемо, с кодом для диагностики. Отдельно и заметно: `DISABLED_BY_USER` («выключено вами»), `DEGRADED/POLICY_NOT_APPLIED` («трафик идёт напрямую»), `FALLBACK_DIRECT`/`FALLBACK_BLOCK`. DNS-состояний и состояний IPv6 Guard в v1 нет.

**Взаимодействие.** rpcd/ACL → Core; не обращается к файлам и процессам напрямую.

**Владение.** Только представление; никаких системных ресурсов.

**Безопасность.** Никаких секретов в DOM/URL; подтверждение для очистки и restore; защита от XSS при выводе имён устройств/серверов; нет произвольных команд.

**Поведение при отказах.** Демон недоступен — понятный экран, а не пустой статус; устаревшие данные помечаются временем; после переподключения — повторная загрузка состояния.

**Критерии приёмки.**
1. Все состояния D-14 отображаются различимо; «выключено пользователем» не выглядит ошибкой.
2. Состояний и предупреждений IPv6 Guard в UI нет; обязательного постоянного предупреждения о незащищённом IPv6 в v1 не требуется (ТЗ §5).
3. Ни одно действие UI не выполняется при отсутствии права.
4. Тест №27 (отсутствие дублирования настроек) проходит.
5. Секреты не попадают в браузер после сохранения.

## 14. Blocklists Manager — **исключён из проекта (superseded U9)**

**Статус: подсистема не реализуется и не откладывается.** Удалены: источники и категории списков, загрузка/обновление/дедупликация/валидация, версии и rollback списков, whitelist, системные исключения, индивидуальные наборы по устройствам и группам, статистика DNS-уровня, Quick Block, `temp_blocklist_off`, DNS-фильтрация.

Историческое описание — №19 (не нормативный документ). Места, где подсистема упоминалась (API, модели, состояния, тесты), помечены superseded.
