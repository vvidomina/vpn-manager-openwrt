## 4. P1-01. Ручной override и `fallbackTag`

### 4.1. Что проверено

Сверено с исходником Xray (`app/router/balancing.go`, `app/proxyman/outbound/outbound.go`, `app/router/strategy_random.go`, `strategy_leastping.go`, `strategy_leastload.go`). Ключевой фрагмент `Balancer.PickOutbound`:

```go
var tag string
if o := b.override.Get(); o != "" {
    tag = o
} else {
    tag = b.strategy.PickOutbound(candidates)
}
if tag == "" {
    if b.fallbackTag != "" {
        return b.fallbackTag, nil
    }
    return "", errors.New("balancing strategy returns empty tag")
}
```

`SetOverrideTarget` подставляет тег через `b.override.Put(target)` без проверки принадлежности набору `selector` и без проверки живости outbound.

### 4.2. Фактическая последовательность выбора

1. `SelectOutbounds()` → набор кандидатов по `selector`.
2. Непустой `override` → тег берётся напрямую, стратегия не вызывается.
3. Иначе — `strategy.PickOutbound(candidates)`.
4. Ветка `tag == ""` → `fallbackTag`; при пустом `fallbackTag` — ошибка и outbound по умолчанию.

### 4.3. Когда `PickOutbound` возвращает пустой тег

- `SelectOutbounds` вернул ошибку при пустом `fallbackTag`;
- стратегия не дала кандидата (нет живых узлов среди `selector`) — и тогда при непустом `fallbackTag` возвращается он, а не пустая строка.

При активном override ветка `tag == ""` **недостижима**.

### 4.4. Два варианта — не эквивалентны

| Вариант | `fallbackTag` при отказе закреплённого сервера | Локальный API Xray | Вердикт |
|---|---|---|---|
| A. Сужение `selector` до тега закреплённого сервера | **срабатывает**: стратегия не находит живого кандидата | не нужен | принят как обязательное ограничение генератора |
| B. `BalancerOverrider` / `SetOverrideTarget` | **не срабатывает** ни при каком отказе | нужен | в v1 не используется |

Вариант B дополнительно: не сохраняется в конфигурации, теряется при перезапуске Xray, требует локального gRPC-хендлера (тот же разрыв, что OQ-14) и при `direct_on_failure=false` лишает ручной режим fail-closed. Отказ закреплённого сервера в варианте B проявляется как ошибка самого outbound.

Вариант A сохраняет штатную обработку недоступности: `random`/`roundRobin` фильтруют кандидатов по Observatory при непустом `fallbackTag`, `leastPing`/`leastLoad` — всегда. Перебора других серверов нет, потому что их нет в `selector`.

Остаточное ограничение варианта A: при холодном старте `random`/`roundRobin` непроверенный закреплённый сервер считается живым; если он мёртв, соединение завершается ошибкой без `fallbackTag` до первого цикла Observatory.

## 5. P2-01 и P2-08. `selector` и `subjectSelector`

Подтверждено исходником: `Manager.Select` сопоставляет теги через `strings.HasPrefix(tag, selector)` — сопоставление **префиксное**, а не по строгому равенству; результат сортируется.

В №18 §7.2 разделены четыре случая:

| Случай | Следствие |
|---|---|
| пустой `subjectSelector` | цикл Observatory не идёт, статусов нет, `fallbackTag` не срабатывает |
| непустой, но не совпавший | то же, но без признака в конфигурации |
| префиксные коллизии (`srv` → `srv2`) | набор кандидатов шире ожидаемого |
| захват несерверных outbound (`direct`, `blackhole`, технические) | в кандидаты попадают посторонние теги |

G4 расширен: набор кандидатов обязан совпадать с набором серверов подписки **ровно**, без DIRECT, `blackhole` и технических outbound, без префиксных коллизий. Проверка объявлена обязательной статической, warning Xray не считается способом обнаружения. Синхронизированы №18 §7.2/§7.3.1, №23 W-03 и сценарии 110–114, №21 §8.

## 7. P2-03. Холодный старт `leastPing`/`leastLoad`

Подтверждено исходником:

- `LeastPingStrategy.PickOutbound` возвращает `""`, если ни один узел не `Alive`; список строится только по `ObservationResult`;
- `LeastLoadStrategy.getNodes` возвращает пустой набор при отсутствии результатов, `PickOutbound` при нуле узлов возвращает `""`.

Следствие: до первых пригодных результатов выбор отсутствует и применяется `fallbackTag`. При `direct_on_failure=true` VPN-предназначенный трафик в этом окне идёт DIRECT.

Зафиксировано: №18 §7.2 п. 2, №20 §8 п. 4, №22 §3, №23 W-03 и новый сценарий 116. Значение `direct_on_failure` по умолчанию не менялось, другая политика не выбиралась. Состояние не представлено как подтверждённая защищённая работа VPN.
