## 1. Условия допуска к любому окну (gate)

Окно не начинается, пока не выполнено **всё**:

1. Утверждён письменный план именно этого окна: цель, команды, ожидаемые результаты, критерий остановки.
2. Есть снимок «до»: `nft list ruleset`, `ip rule`, `ip route`, `uci export`, `ubus list`, состояние служб, `df -h`, свободная RAM.
3. Есть проверенный откат для каждого шага, выполнимый без сети (если сеть пострадает).
4. Подтверждено, что кратковременная деградация доступа допустима; определено максимальное время перерыва.
5. Есть доступ к устройству не только по SSH через проверяемый канал (альтернатива: локальный доступ/консоль), иначе риск «запертой двери».
6. Все секреты в выводе маскируются тем же фильтром, что в `stage1/collect.sh`; логи окна не попадают в Git.
7. Явно указано, какие файлы/правила будут созданы и как удалены.
8. Ни один шаг не меняет `network`/`firewall` UCI (ТЗ §4, §5); если шаг это требует — он не выполняется, а выносится на согласование.

**Немедленная остановка окна:** рост числа ошибок dnsmasq; потеря default route дольше объявленного перерыва; трафик в мёртвый порт; непредусмотренное изменение сетевых настроек, включая IPv6 (v1 их не меняет и не измеряет); падение демона без восстановления; заполнение overlay.

### W-03. Observatory, стратегии и fallback (T-02) — редакция U9

**Цель:** подтвердить, что штатный Xray обеспечивает согласованную модель доступности без собственного менеджера здоровья, и зафиксировать границы fail-closed.
**Метод:** read-only инвентаризация версии Xray; проверка поддержки `observatory`, `probeUrl`/`probeURL`, `enableConcurrency`, четырёх стратегий, `fallbackTag`, outbound `blackhole`; на изолированной сборке — конфигурация с несколькими серверами, `probeInterval: "300s"`; наблюдение первого цикла и последующих; отдельно `random`, `roundRobin`, `leastPing`, `leastLoad` и их фактическое различие; пустой и несовпавший `subjectSelector`; запуск без `observatory` при заданном `fallbackTag`; падение одного сервера сразу после успешной проверки; недоступность всех серверов при `direct_on_failure=true` и `false`; восстановление серверов и судьба открытых соединений; замер длительности цикла на большой подписке (сценарий 105); проверка локального gRPC `ObservatoryService.GetOutboundStatus`: привязка listener к `127.0.0.1`, состав `api.services`, поля ответа, пустой результат и ошибка API (сценарии 119–124); проверка честности подписи `leastLoad` и отсутствия `burstObservatory` (сценарии 126–130).
**Критерии:** непроверенные outbound считаются доступными для `random`/`roundRobin`; `leastPing`/`leastLoad` без результатов не работают как `random`, а дают `fallbackTag` (сценарий 116); 300 с — пауза после набора; при `false` нет выхода в DIRECT; `fallbackTag` без Observatory не стартует и это видно на `xray -test`; пустой селектор даёт warning и отключает fallback; `leastPing` и `leastLoad` при обычной `observatory` либо различаются измеримо, либо их эквивалентность зафиксирована (OQ-15, вариант A: подпись честная, `burstObservatory` не добавляется); мгновенный failover не наблюдается и не обещается. Наблюдаемость: listener только на `127.0.0.1`, в `api.services` только `ObservatoryService`, пустой список не трактуется как ошибка API.
**Статическая проверка — обязательный критерий:** непустой `subjectSelector` с точным покрытием серверных outbound без префиксных коллизий, состав `selector` без DIRECT/`blackhole`/технических outbound, существование outbound с тегом `fallbackTag` (G4–G5, сценарии 110–115). Warning Xray сам по себе критерием не является.
**Ограничение:** измеряется фактическое поведение Xray; собственные счётчики отказов и собственная проба не создаются. Протокол фиксирует версию Xray и фактические значения.

### W-05. Ручной override сервера (T-03) — редакция U9
**Цель:** проверить override одного сервера без собственного failover.
**Метод:** закрепить сервер при активном VPN; проверить по конфигу, что override реализован сужением `selector` балансировщика (вариант A), а не `SetOverrideTarget` (вариант B: `fallbackTag` не срабатывает, №18 §7.4.1); убедиться, что балансировщик использует только его; погасить закреплённый сервер; проверить срабатывание `fallbackTag` (DIRECT при `direct_on_failure=true`, `blackhole` при `false`) и отсутствие перебора других серверов; вернуть автоматический режим — проверить восстановление выбранной стратегии; успешно обновить подписку, в которой выбранный сервер остался — проверить сохранение override и перепривязку к новому `srv_id`; обновить подписку без этого сервера — проверить сброс в `auto`; проверить обновление с изменённым порядком серверов.
**Критерии:** нет собственного перебора серверов; в UI однозначно видно режим; override сохраняется только при точном совпадении нормализованной конфигурации; при исчезновении сервера режим автоматический; поведение открытых соединений фиксируется, но не обещается.

### 4.1 Условия допуска (U9)

| Условие | Что проверяет | Что открывает при успехе | Что **не** открывает |
|---|---|---|---|
| **C3-13 / W-11** | передача identity через rpcd: действующая сессия + системный UID, игнорирование поля `user`; штатные rpcd ACL | функциональную реализацию API | ничего сверх API: отдельной системы identity нет |
| **Read-only аудит сетевой части** | трафик роутера не идёт через туннель; маршрутизация клиентов соответствует модели | подтверждение сетевого поведения | кодирование и публикацию |

**Правило:** успех одного окна не считается успехом другого; результаты указываются раздельно (окно, дата, критерий).

**Снято в U9:** прежнее условие W-14 (точность привязки DNS↔устройство) и связанное с ним включение индивидуальных Blocklists/DNS-части D3 не действуют — этих функций в U9 нет. Прежняя формулировка «что доступно до W-14» (общий набор Blocklists, whitelist, `temp_blocklist_off`, S2/S3, Quick Block) относится к удалённым механизмам и сохранена только в истории (№33).

### 4.2 Исключение трафика роутера — **не проверено (U9)**

Отдельного P0-gate и подсистемы маркировки служебного трафика в U9 нет. Остаётся требование **REQ-165**: собственный трафик роутера не направляется через VPN-туннель приложения (№18 §2, §3.1).

**Метод:** read-only аудит в составе окна VPN-маршрутизации, с отдельным разрешением владельца. Проверяется каждый поток из перечня №18 §3.1:

1. загрузка подписки и bootstrap;
2. плановое обновление по `crond`;
3. пробы Observatory;
4. внешнее соединение самого туннеля;
5. DNS-запросы `dnsmasq` к upstream;
6. системные обращения OpenWrt (NTP, пакеты).

Для каждого фиксируется фактический путь (интерфейс, таблица, наличие метки перехвата) без изменения настроек.

**Критерий:** ни один из потоков не попадает в перехват и балансировщик; отдельно подтверждено, что соединение Xray к серверу не захватывается повторно (сценарий 103); при обнаружении попадания реализация останавливается до отдельного решения.

**Ограничение:** отсутствие проверки не даёт права утверждать, что требование выполнено на устройстве. Наличие требования в документе не является доказательством P0.

### 4.3 Существующие UDP-сессии при смене пути (R-05) — **не проверено**

Утверждённого поведения нет; правила TCP на UDP не переносятся. В U9 проверяется фактическое поведение при переходе в `fallbackTag` (DIRECT или `blackhole`) и после восстановления серверов: сохраняются ли существующие UDP-сессии, прекращаются ли они, возникает ли утечка в DIRECT при `direct_on_failure=false`.

**Критерий:** поведение описано по факту, без обещаний; при `false` утечки UDP в DIRECT нет. Quick Block в U9 отсутствует, поэтому его влияние не проверяется.

### 9.1 Сценарии архитектурного усиления U9-H (описаны, не выполнялись)

Нумерация продолжает §9. Каждый сценарий содержит предусловия, действия, ожидаемый результат, диагностические признаки и статус. **Ни один не выполнялся**; окна W не запускались.

Сценарии 109–118 добавлены по итогам независимого ревью U9-H (U9-H1); сценарии 119–130 — по решениям OQ-14 (вариант B) и OQ-15 (вариант A), отчёт №37; сценарии 131–136 — по итогам ревью №38 (U9-H2, отчёт №39); сценарии 137–141 — по итогам независимого ревью U9-H2 (U9-H3, отчёт №41); сценарии 142–152 — по четырём решениям владельца (дедлайн gRPC 2 с, `grace` 2 с, `respawn 3600 5 5`, singleton через `flock`) и заданию №46 (отчёт №43).

#### 135. Расчёт свежести и состояние `stale`

| Поле | Значение |
|---|---|
| Предусловия | изолированный стенд с подменяемым ответом API или управляемыми часами; известны `probeInterval`, `enableConcurrency`, фактическое `N` (число outbound после префиксного сопоставления) и `max_probe_time`; TTL рассчитан по формуле №20 §7.2 отдельно для concurrent и sequential |
