## 3. Выбранная архитектура и альтернативы

### 3.1. Выбор

**Основной вариант A** `[П]` — cgo-обвязка над штатными `libubus`/`libubox` внутри процесса `vpnmand`; демон сам регистрирует все объекты `vpnmanager*` и сам повторно проверяет права.
**Резервный вариант B** `[П]` — минимальный C-адаптер (`ubus_bridge.c`) с той же моделью, но с изолированным cgo-слоем.

### 3.2. Почему не альтернативы

| Вариант | Причина отказа |
|---|---|
| C. rpcd/ucode-адаптер | объекты регистрируются в процессе rpcd (`/usr/share/rpcd/ucode/*.uc`), бизнес-логика оказалась бы вне демона; потребовался бы новый IPC «rpcd → vpnmand» (запрещён); демон не смог бы перепроверить права, так как `req->acl` и sid остаются в rpcd; ucode не владеет Xray, `flock` и nftables |
| D. чистый Go без cgo | регистрация объектов и разбор peer-атрибутов означают собственную реализацию бинарного TLV-протокола ubusd без стабильного публичного контракта; сторонние Go-библиотеки клиентские, требуют новой зависимости (в №56 запрещено) и не проверены для 25.12.6; ошибка в разборе атрибутов ломает W-11 |

### 3.3. Технические основания выбора A

1. `struct ubus_request_data` содержит `peer`, `seq` и `struct ubus_acl_key acl {user, group, object}` — поля `acl` заполняются из `UBUS_ATTR_USER`/`UBUS_ATTR_GROUP` в `ubus_process_invoke()`; доступны только нативному обработчику.
2. ACL остаётся штатным (ubusd + rpcd), приложению не нужен собственный слой прав.
3. События, отложенные ответы (`ubus_defer_request`/`ubus_complete_deferred_request`) и таймауты — штатные механизмы libubus.
4. Зависимости — пакеты базовой системы OpenWrt (`libubus`, `libubox`, `libblobmsg-json`), уже присутствующие на устройстве; новых процессов и портов не появляется.
5. Переход A→B не меняет API, ACL и схему объектов — только слой cgo.

### 3.4. Издержки, зафиксированные в плане

Единый поток `uloop` для всех вызовов libubus; запрет блокировки обработчика; копирование значений из `blob_attr` до возврата; cgo и `CGO_ENABLED=1` с SDK-тулчейном; несовместимость ABI между релизами; сигналы остаются в Go, C-цикл их не перехватывает.

## 6. W-11: результат анализа и статус

### 6.1. Что выяснено

1. `req.acl.user` — это uid **процесса-отправителя invoke** (при HTTP-вызове — `uhttpd`, обычно root), а не пользователь LuCI. Атрибуты ставит `ubusd` (`ubusd_forward_invoke`), поэтому подделать их из браузера нельзя, но и идентифицировать человека по ним нельзя.
2. `SO_PEERCRED` на соединении с `ubusd` возвращает **ubusd**, а не автора запроса: у демона одно AF_UNIX-соединение с брокером. Собственный сокет запрещён §4.2 задания, значит peer credentials в смысле «UID вызывающего» через ubus недоступны.
3. Доверенная идентичность есть только в связке: `ubus_rpc_session` (sid) + `session.access`/`session.get` на стороне rpcd. `uhttpd-mod-ubus` проверяет `session.access` до вызова и, по документации и разъяснению мейнтейнера LuCI, **сам** добавляет sid в аргументы вызова, отклоняя попытку передать sid в теле HTTP-запроса `[Т]`.
4. Поле `user`/`username`/`actor`/`uid` в теле запроса не участвует в авторизации и должно игнорироваться.

### 6.2. Предложенный механизм `[П]`

На каждый вызов: извлечь sid → при отсутствии sid разрешить только при `req.acl.user == "root"` (локальный root-CLI, `source=cli`) → при наличии sid отклонить default session `000…0`, вызвать `session.access {scope:"ubus", object, function}` с таймаутом 2 с и fail-closed, при необходимости получить `actor` через `session.get`; требуемую группу (`read`/`control`/`admin`) сверить с реестром §5.1 плана.

### 6.3. Статус

W-11 **остаётся блокирующим** (`RT-16`, `RB-07`). Составлен тест из 12 шагов (план §6.4) с явными критериями: шаги 4–7 и 11 должны давать отказ; шаг 10 — корректного субъекта в аудите. Тест **не выполнялся**: подключение к роутеру в №56 запрещено. До прохождения W-11 функциональная реализация API не начинается (№12 §9 п.5).

Ослабление модели (доверие `acl.user` как имени пользователя, доверие полю `user`, добавление daemon-токена) не предлагается.
