# Документ №4. План разработки VPN Manager

Дата: 22.11.2026
Основание: ТЗ §21 (12 этапов), результаты документов №1–№3.
Статус: **план, не разрешение на реализацию.** Решения Q-01…Q-13 утверждены 22.11.2026 (документ №5, ред. 2); кодирование начинается только после отдельного разрешения пользователя.

---

## 1. Принципы плана

1. **Порядок диктуется зависимостями, а не удобством.** Нельзя писать UI раньше API, API раньше модели данных, а модель — раньше зафиксированных решений (они утверждены 22.11.2026, документ №5 ред. 2).
2. **Каждый этап заканчивается проверяемым результатом.** «Готово» = артефакт + пройденный набор проверок, а не «код написан».
3. **Опасные операции (сеть) не тестируются впервые на рабочем роутере.** Сначала — изолированная среда, потом устройство, и только потом с реальным интернетом пользователя.
4. **Никаких фиктивных чисел.** Все пороги, длительности и метрики появляются после измерений (ТЗ §13, §19.3).
5. **Обратная совместимость не требуется.** Старый проект не мигрируется; переносится только проверенная функциональность.

**Цель:** получить факты вместо предположений и закрыть измеримую часть T-01…T-13.
**Работы:**

### Этап 2. Проектирование модели данных, состояний и API
**Цель:** зафиксировать контракты до кода.
**Работы:**
- модель сущностей (подписка, сервер с устойчивым ID, профиль, назначение, устройство, DNS-политика, UDP-политика, предпочтение, фактическое состояние, транзакция);
- матрица владения ресурсами (кто единственный писатель для nftables / fwmark / ip rule / route / Xray config / dnsmasq / состояния);
- модель состояний настройки (`Saved / Applied / Pending reconnect`) и состояний системы (`OK / DEGRADED_DIRECT / EMERGENCY_DIRECT / WAN_DOWN / DNS_DEGRADED`);
- схема API (операции, коды ошибок, идемпотентность, блокировки);
- схема хранения (что в UCI, что в JSON, версия схемы, миграции);
- алгоритм устойчивого ID сервера;
- модель транзакции apply/rollback и восстановления после перезагрузки (D-06: подготовка, валидация, preflight, trial, commit);
- контракт ubus/rpcd: объекты, методы, коды ошибок, матрица ACL (D-05);
- контракт IPv6-стража: обнаружение глобального IPv6, безопасное ограничение клиентского выхода, состояние предупреждения (D-01);
- модель типа подписки Restricted/обычная и источник значения (D-07);
- схема backup с версией схемы и правилами restore (D-10);
- формат кольцевого журнала Flash и правила rate limit/маскирования (D-09).
**Результат:** документ «Архитектура и контракты» + ADR на каждое неочевидное решение.
**Критерий завершения:** по документу можно написать два независимых модуля и они совместимы; для каждого требования ТЗ указано, где оно реализуется.
**Зависимости:** этапы 0, 1.
**Статус 22.11.2026: выполнен без кодирования** — документы №10 (архитектура, диаграммы, владение ресурсами, матрица ошибок), №11 (13 контрактов компонентов), №12 (ubus API и ACL), №13 (модели данных и состояний), №14 (реестр решений, зависимость от W-01…W-09, матрица приёмки, готовность). Добавлена модель состояния «VPN выключен пользователем» (D-14, T-14) по факту ручной остановки Xray. Ждёт проверки владельцем.

### Этап 3. Каркас Go-демона + Policy Manager + Xray lifecycle + Recovery
**Цель:** минимально работающее ядро: поднять Xray, поставить/снять перехват, безопасно применить конфигурацию.
**Работы:**
- структура демона, модули, внутренняя шина/очередь операций, единая блокировка изменений;
- адаптеры: UCI, ubus, netlink, nftables, process/service, storage;
- Policy Manager: идемпотентное применение nft+ip rule+route, транзакции, откат;
- VPN Manager: генерация конфига Xray, `xray -test`, preflight outbound, staged apply по D-06 (trial с проверкой фактического трафика, commit/rollback, canary как опция);
- ubus/rpcd-сервер демона: регистрация объекта, методы, проверка прав на стороне демона, разделение чтения/изменения (D-05);
- IPv6-страж: детект глобального IPv6, ограничение клиентского выхода, состояние для UI (D-01);
- Recovery Controller: последняя рабочая конфигурация, восстановление после сбоя/перезагрузки, защита от циклов;
- журнал транзакций; двухконтурное журналирование (RAM + кольцо Flash 256 КБ + 1 ротация, D-09).
**Результат:** демон, который на тестовой среде умеет: включить перехват, применить конфиг, откатиться при ошибке, восстановиться после перезапуска.
**Критерий завершения (обязательные проверки):**
1. Искусственная ошибка конфига Xray → правила не поднимаются/снимаются, интернет есть.
2. Искусственная ошибка nft → система остаётся в DIRECT, правила не остаются «полуприменёнными».
3. Повторное применение не создаёт дублей nft/ip rule/route.
4. Перезапуск демона и перезагрузка → согласованное состояние, без накопления правил.
5. Нет пути «трафик → мёртвый локальный порт» ни в одном сценарии (проверяется инструментированно).
**Зависимости:** этап 2.

### Этап 4. Импорт, подписки, серверы, профили
**Цель:** данные и их корректное обновление.
**Работы:** импорт VLESS/VMess/Trojan/URL/Base64/Happ deeplink/подмножество Xray JSON; отчёты импорта; устойчивые ID; пользовательский порядок; транзакционное обновление; профили (routeOrder, 6 списков, DomainStrategy, GlobalProxy); Restricted JSON по D-07 (явный маркер провайдера или выбор пользователя, без эвристик); Pending reconnect и приоритеты подписок по D-13; компилятор правил с детерминированным порядком.
**Результат:** импорт и хранение данных + генерация политики маршрутизации.
**Критерий завершения:** тесты ТЗ §19.2 №2–10 (кроме UI-части) проходят на тестовой среде.
**Зависимости:** этап 3 (нужен генератор конфига).

### Этап 5. Устройства, маршрутизация, UDP
**Цель:** пользовательская логика маршрутизации по устройствам.
**Работы:** обнаружение (DHCP/neigh/Wi-Fi/FDB), MAC-идентичность, offline-записи, объединение, Always DIRECT; per-device правила в Policy Manager; UDP Manager (3 режима, allowlist, Quick Block, состояние поддержки сервера); трафик роутера; клиентский IPv6-страж (D-01); проверка поведения при offload и, при доказанной необходимости, точечное исключение трафика (D-12/T-12).
**Результат:** работающая политика «устройство → профиль → маршрут».
**Критерий завершения:** тесты №11–13; Always DIRECT полностью обходит пользовательские правила (включая Quick Block); UDP не даёт скрытого direct egress.
**Зависимости:** этап 4.

### Этап 6. DNS Manager
**Цель:** единая DNS-подсистема.
**Работы:** цепочки (Yandex DoH, ISP fallback, Remote DNS через VPN, fallback Remote), bootstrap, кэш, защита от циклов, перехват клиентского DNS, DoT/известные DoH, состояние fallback для UI, выбор транспорта (https-dns-proxy или собственный DoH); согласование AAAA-ответов с IPv4-only политикой так, чтобы DNS не создавал IPv6-обход (D-01).
**Результат:** DNS работает предсказуемо, состояние наблюдаемо.
**Критерий завершения:** тесты №14–15; «какой upstream использован» доказуемо; fallback отображается; петли отсутствуют.
**Зависимости:** этап 3 (Policy Manager для перехвата 53), этап 5 (классификация DIRECT/PROXY для DNS-запросов).

### Этап 7. Failover, мониторинг, диагностика
**Цель:** устойчивость.
**Работы:** WAN-детект, VPN-проверки через конкретный outbound, сервисные пробы, параметры 30 с / 8 с / ≤3 параллельных и порог 2 независимых fail (D-02), автовозврат 3 success × 5 мин и ручной выбор без гистерезиса (D-03), preferred vs active, поведение при полном отказе (DEGRADED_DIRECT с предупреждением), conntrack как диагностика с порогом 80 % (D-11), журнал событий, экспорт диагностики с маскированием.
**Результат:** система сама различает «нет WAN», «нет сервера», «нет DNS» и ведёт себя по ТЗ.
**Критерий завершения:** тесты №16–21.
**Зависимости:** этапы 3–6.

### Этап 8. LuCI
**Цель:** интерфейс по ТЗ §14.
**Работы:** каркас (верхняя панель + 7 вкладок), вкладки, состояния/предупреждения, прогресс операций, подтверждения, мобильный layout, маскирование секретов; вызовы только через ubus/rpcd с ACL (D-05); постоянное предупреждение о незащищённом IPv6 (D-01); предупреждение о секретах в backup (D-10).
**Результат:** UI, не дублирующий настройки.
**Критерий завершения:** тест №27 + аудит «один параметр — одно место управления»; предупреждения постоянны и заметны; при недоступном демоне UI не зависает.
**Зависимости:** этап 2 (API), фактически — после этапов 3–7 (иначе нечего показывать).

### Этап 9. Пакетирование, backup/restore, установка/обновление/удаление
**Цель:** поставляемый продукт.
**Работы:** APK-пакет (`aarch64_cortex-a53`, `mediatek/filogic`), зависимости, `conffiles`, проверка свободного места, миграции схемы, backup/restore по составу D-10 с проверкой версии схемы, pre-flight и управляемая очистка по D-08, кольцевой журнал по D-09, удаление без повреждения системы.
**Результат:** устанавливаемый пакет.
**Критерий завершения:** тесты №1, №25, №26 на чистой сборке.
**Зависимости:** этапы 3–8.

### Этап 10. Полный тест-план и измерения
**Цель:** доказательства, а не заявления.
**Работы:** прогон 27 тестов ТЗ §19.2, измерения §19.3, запись результатов.
**Результат:** протокол испытаний.
**Критерий завершения:** все тесты пройдены либо явно перечислены непройденные с причиной.
**Зависимости:** этапы 3–9.

### Этап 11. Релиз-кандидат и приёмка
**Цель:** приёмка по ТЗ §20.
**Работы:** финальная сборка, приёмка по критериям §20, инструкция по восстановлению.
**Результат:** RC + подписанный протокол приёмки.
**Зависимости:** этап 10.

## 4. Тестирование

### 4.1 Уровни
1. **Unit** — компилятор правил, парсеры, алгоритм ID, валидаторы (порты, CIDR, MAC), модель состояний.
2. **Интеграционные на изолированной среде** — Policy Manager на netns/контейнере (nft, ip rule, tproxy), генерация конфига + `xray -test`, транзакции/откат, восстановление.
3. **На устройстве (лабораторно)** — реальный nftables/ядро/PPPoE, измерения, все 27 сценариев.
4. **На устройстве (пользовательский сценарий)** — после приёмки.

### 4.2 Обязательные «проверки на отказ» (не входят в список ТЗ напрямую, но нужны)
| Проверка | Ожидание |
|---|---|
| Ошибка конфига Xray при каждом применении | система остаётся в последней рабочей конфигурации, нет цикла apply/rollback |
| Ошибка nft посередине | нет «полуприменённой» политики, нет трафика на мёртвый порт |
| Перезагрузка во время apply | после загрузки — последняя рабочая конфигурация, транзакция помечена как прерванная |
| OOM/убийство демона | procd поднимает, состояние восстанавливается, правила не дублируются |
| Заполнение Flash | система не падает, журналы ограничены, есть предупреждение |
| Одновременные операции (UI + фон) | сериализация, нет потерянных изменений |
| Смена WAN-прототипа (pppoe→dhcp) | детект WAN продолжает работать |
| Чужой include в firewall | обнаружен и отражён в отчёте, не ломает применение |

### 4.3 Инструменты
- Go: `go test` для unit; отдельный harness для nft/ip в netns.
- `xray run -test` — валидация конфигов.
- На устройстве: `logread`, `nft list ruleset`, `ip rule`, `ip route`, `/proc/net/*`, `conntrack`, собственный журнал демона.
- Для измерений: `iperf3` (устанавливается на время теста с согласия пользователя) или загрузка известного объёма.

## 6. Оценка объёма (без календарных дат)

Даты не назначаются: ТЗ запрещает фиктивные числа. Решения Q-01…Q-13 больше не являются неизвестным: v1 — IPv4-only, UI — ubus/rpcd, протоколы определены, поэтому прежняя вилка «IPv6 может добавить 30–50 %» снята. Относительная оценка трудоёмкости (в условных единицах «1 = этап 1»):

| Этап | Относительный объём | Комментарий |
|---|---|---|
| 0 | 0.5 | переговоры + ADR |
| 1 | 1 | измерения и сбор логов |
| 2 | 2 | модель, API, матрица владения |
| 3 | 4 | ядро, самый рискованный этап |
| 4 | 3 | парсеры + компилятор + ID |
| 5 | 3 | устройства, UDP, per-device nft |
| 6 | 3 | DNS с двумя цепочками |
| 7 | 2 | failover + диагностика |
| 8 | 3 | 7 вкладок + состояния |
| 9 | 2 | apk, миграции, backup |
| 10 | 2 | прогон + измерения |
| 11 | 1 | приёмка |

Полная поддержка IPv6 в v1 не реализуется (D-01), поэтому сетевые этапы не увеличиваются на 30–50 %. Взамен добавляется небольшой обязательный объём: IPv6-детект, предупреждение, ограничение клиентского выхода и его проверки (T-01), плюс испытания T-02…T-13.

## 7. Риски плана и способы управления

| Риск | Влияние | Управление |
|---|---|---|
| Этап 3 окажется сложнее ожидаемого (staged apply без разрыва) | сдвиг всего плана | начать с «минимального безопасного» варианта: короткое окно + гарантированный откат, оптимизация позже |
| Проверка e2e до commit | может сорвать staged apply | закрыто D-06: preflight + trial + автоматический откат; длительность измерить (T-06) |
| Клиентский IPv6 обходит политику | утечка трафика вне VPN | D-01: детект, предупреждение, безопасное ограничение; проверить T-01 |
| Flash/RAM окажутся тесны | переработка сборки | измерить на этапе 1, заложить `-s -w`, лимиты журналов |
| Offload конфликтует с per-device | неверная работа политики | D-12: A/B (T-12), сначала точечное исключение; глобальное отключение только с согласованием |
| Отсутствие логов старого проекта | аудит остаётся частично гипотетическим | собрать логи (документ №6) до начала этапа 3 |
