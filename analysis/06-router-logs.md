### 2.2 Ключевые наблюдения состояния (с интерпретацией)

**Наблюдение L-01. Xray работает, но перехват не поднят.**
Факт: процесс `/usr/bin/xray run -config /etc/xray/config.json -format json` жив (`after-restore:317`), слушает `:12345` и `:5353` (`:374-388`). При этом:
- `nft list tables` содержит только `table inet fw4` (`:236`) — таблицы проекта (`inet xray`) нет;
- `ip rule` содержит только штатные записи `0/32766/32767` (`:295-299`) — правила `fwmark ... lookup 777` нет.

Вывод: конфигурация «Xray запущен, политика не применена» — штатное безопасное состояние (трафик идёт напрямую). Причина именно такого состояния **на 19.11** по снимку не определяется: это может быть `tproxy.enabled=0`, пустой canary, сработавший авто-откат (`xray-manager:220-236`) или аварийный режим (`emergency=1`). **Требуется `/etc/xray/emergency`, `/etc/xray/state`, `/tmp/xray-state.vol` и `logread -e xray-manager|xray-watchdog|xray-tproxy`** — без них состояние 19.11 не объясняется.

**Уточнение 22.11.2026.** Наблюдение L-01 относится к снимку 19.11, когда Xray работал. Отсутствие Xray на обследовании 22.11 — **намеренная ручная остановка владельцем** для возврата прямого доступа, а не отказ и не «неизвестная авария»; `logread` после 08:36 просто не содержит записей остановленного процесса. При этом файлы `/etc/xray/state` (`mode=vpn`) и `/tmp/xray-state.vol` (`alive=1`) остались прежними — это подтверждает дефект механизма состояния (S1-03), а не сбой Xray.

**Наблюдение L-02. DNS LAN идёт к резолверам провайдера, а не через VPN.**
Факт: `dhcp.@dnsmasq[0].resolvfile=/tmp/resolv.conf.d/resolv.conf.auto`, `noresolv=0` (`:155-156`); в `resolv.conf.auto` — `78.37.77.77`, `212.48.197.77` (`:191-195`); `server=` в dnsmasq содержит только записи `mask.icloud.com` (`:163`).
Сопоставление с кодом: `xray-dns` пишет upstream в `/tmp/xray-dns.upstream` (`xray-dns:23,40-41`), который dnsmasq не читает → переключение «xray/fallback» ни на что не влияет (баг **B-04** документа №2). Наблюдение независимо подтверждает B-04 на реальной системе.
Достоверность: **высокая** (конфигурация + код согласуются). Конкретные DNS-запросы «наружу» в журналах не зафиксированы — их нет.

**Наблюдение L-03. Xray-DNS на `127.0.0.2:53` не слушает.**
Факт: слушатели Xray — только `:5353` и `:12345` (`:169-183,375-388`); `127.0.0.2:53` отсутствует. Генератор конфига объявляет inbound `dns-local` на `127.0.0.2:53` (`build-config.uc:147-155`).
Следствие: проверка `xray-dns check` (`xray-dns:26,68-78`) всегда неуспешна → `dns_ok=0` → watchdog держит upstream в `fallback` (`xray-watchdog:236-250`). Это объясняет L-02 и делает состояние DNS самоподдерживающимся («всегда fallback»).
Достоверность: **высокая** по факту отсутствия слушателя; причина отсутствия — **не установлена** (варианты: работающий `config.json` собран иначе; bind не удался; инбаунд удалён вручную). Требуется `cat /etc/xray/config.json` (с маскированием) — P-02 документа №2.

**Наблюдение L-04. IPv6 активен внутри LAN, но глобального IPv6 нет (уточнено 22.11.2026).**
Факт по снимкам 19.11: IPv6 forwarding=1 (`:121-122`), ULA `fd0a:9818:c7b2::/60`, `wan6 proto=dhcpv6` (`:96-129`), dnsmasq слушает на IPv6-адресах (`:166-183`).
**Уточнение по обследованию 22.11.2026 (документ №8 §1.4):** `wan6` не поднялся (`up=false pending=true`), глобального адреса и префикса нет, IPv6 default route нет, `ip -6 route get 2606:4700:4700::1111` → `Network unreachable`; есть только ULA, RA с `lifetime 0` («No default route present…» в журнале odhcpd) и внутренний IPv6 клиентов. То есть прежняя формулировка «IPv6 у провайдера подтверждён» **неверна**: ULA и RA были приняты за IPv6-доступ.
Сопоставление с кодом: nft-цепочки проекта содержат `meta nfproto != ipv4 return` (`xray-tproxy:11,130,141`) → IPv6 не перехватывается (баг **B-08**, архитектурный).
Достоверность: **высокая** по составу адресов/маршрутов. Объём «утёкшего» IPv6-трафика равен нулю в текущем состоянии; риск латентный: fw4 пропускает IPv6 в `forward` без ограничения семейства (S1-01).

**Наблюдение L-05. Flowtable offload включён.**
Факт: в `fw4` присутствует `flowtable ft` с `flags offload` и устройствами `lan2-4`, `phy0-ap0`, `phy1-ap0`, `wan` (`:214-220`).
Следствие: политика, рассчитанная на каждый пакет (per-device ограничения, UDP-блокировка), может не применяться к уже установленным offloaded-потокам (риск **R-01**). Требует проверки (M-09).

**Наблюдение L-06. Остатки прежних VPN-стеков и висячие include.**
Факт (25.12.6): в UCI firewall остались include от passwall2 на `/var/etc/passwall2*.include` (`:287-291`) — этих файлов после загрузки нет (tmpfs), сам passwall2 не установлен. В `/etc/config`: `v2raya`, `zapret`, `zapret.tmp`, `*.apk-new` (`:330-350`). В `rt_tables` — `100 zeroblock` (`:305`).
Факт (25.12.5): таблицы `zapret` и `zapret2` в nftables (`audit-2026-11-19.txt:248-340`), cron `/opt/zapret-manager-luci/backend.sh` каждые 2 минуты (`:646-652`), установлен `https-dns-proxy` + `luci-app-https-dns-proxy` (`:453,559`).
Следствие: минимум один посторонний владелец firewall (в прошлом — два) и источник скрытых изменений раз в 2 минуты. Это соответствует пункту P-02 реестра «несколько компонентов меняют firewall» — но уже на уровне окружения, а не только кода (баг **B-14**).
Тяжесть последствия (`fw4` не применяет правила при отсутствующем include) **не подтверждена** — нужен `fw4 print` + `logread -e fw4` после reload.

**Наблюдение L-07. Порог conntrack в watchdog ниже системного максимума.**
Факт: `nf_conntrack_max` = 15360 (`after-restore:222`), было 65536 на 25.12.5 (`audit-2026-11-19.txt:296`). Watchdog считает отказом `ct > 6000` (`xray-watchdog:21,227-228`).
Следствие: при обычной нагрузке возможен ложный аварийный режим с отключением VPN (**B-15**). В снимках `nf_conntrack_count` = 255 и 97 — то есть в простое далеко от порога; момент достижения 6000 не зафиксирован (журналов нет).

**Наблюдение L-08. Следы длительной работы без перезагрузки на прежней прошивке.**
Факт: uptime 5 520 685 с (63.9 сут) на 25.12.5 (`audit-2026-11-19.txt:9`).
Что это даёт: система в целом была стабильна на уровне ядра/загрузки — 64 дня без ребута. Это **не** опровергает периодические потери интернета (они не требуют перезагрузки), но снижает вероятность версии «роутер сам перезагружается». Версия «watchdog/manager уводят систему в DIRECT» выглядит правдоподобнее, но **не доказана**.

**Наблюдение L-09. Состав установленного после восстановления.**
Факт: 183 пакета, из них релевантны `xray-core-26.10.21-r1`, `dnsmasq-2.93-r2`, `firewall4`, `nftables-json-1.1.6`, `ip-full-6.18.0`, `ucode`, `rpcd-mod-*`, `curl`, `flock`, `pgrep`, `timeout`, `dig`; отсутствуют `jq`, `python3`, `openssl`; `logrotate` в этой конфигурации не установлен, но доступен в официальном feed packages-25.12 для `aarch64_cortex-a53` (`after-restore:414-624`). `https-dns-proxy` **не установлен** (был на 25.12.5).
Факт: init-скрипты `xray-watchdog` и `xray-led` **отсутствуют**, `xray` присутствует и включён (`:625-633`).
Следствие: watchdog/monitor/led в этой конфигурации **не работали как службы**, несмотря на наличие кода. То есть часть защитных механизмов старого проекта на момент снимка не была активна. Это важное ограничение для интерпретации: наблюдаемое состояние (`tproxy` не поднят) могло быть следствием ручного включения без супервизии.

**Наблюдение L-10. DNS-резолвинг на роутере работает при «неправильной» цепочке.**
Факт: `nslookup example.com 127.0.0.1` возвращает ответ (`:640-644`), прямой доступ (wget generate_204) — код 0 (`:636-639`).
Следствие: базовый интернет и DNS исправны; проблемы, если они были, лежат в плоскости политики (перехват/маршрутизация/выбор сервера), а не в подключении.

## 5. Что нужно собрать (read-only команды) и что каждая даёт

Часть команд совпадает с техническими проверками T-08, T-09 (документ №5, часть B); команды прежней проверки T-01 (IPv6) в v1 не выполняются и в этот перечень не входят. Сбор не меняет состояние устройства; всё, что требует сетевого вмешательства, выполняется только в согласованном тестовом окне с планом отката.

Все команды — **только чтение**. Ни одна не меняет конфигурацию, не перезапускает службы, не устанавливает пакеты. Выполнять на устройстве по SSH, вывод сохранять в файл.

### 5.1 Журналы (главное)
| Команда | Что даёт |
|---|---|
| `logread > /tmp/collect/logread.txt` | системный журнал: старты/падения служб, procd respawn, ошибки |
| `logread -e xray | tee /tmp/collect/xray.txt` | всё, что писали `xray-manager`, `xray-tproxy`, `xray-watchdog`, `xray-dns`, `xray-update`, сам Xray |
| `logread -e dnsmasq > /tmp/collect/dnsmasq.txt` | рестарты dnsmasq, ошибки upstream, DHCP |
| `logread -e fw4 > /tmp/collect/fw4.txt` | ошибки применения firewall, в т.ч. по отсутствующим include (проверка B-14) |
| `logread -e netifd -e pppd > /tmp/collect/wan.txt` | поднятие/падение PPPoE, смена адреса — сопоставление с «пропал интернет» |
| `logread -e odhcpd -e hostapd > /tmp/collect/lan.txt` | DHCP/RA, ассоциации Wi-Fi (для модуля устройств) |
| `dmesg > /tmp/collect/dmesg.txt` | ядро: OOM, ошибки nft/conntrack, tproxy, драйверы |
| `dmesg | grep -iE "oom|killed process|out of memory"` | признаки нехватки памяти |
| `cat /root/state.log /root/state.log.1 2>/dev/null` | собственный журнал старого проекта (BOOT/EVENT/heartbeat) — **самый ценный источник** о потерях интернета |
| `cat /tmp/state.ring 2>/dev/null` | последние ~20 строк мониторинга (если система не перезагружалась) |

**За какой период:** минимум 7 суток непрерывной работы, включая хотя бы один инцидент. Если журнал уже прокрутился — включить постоянное сохранение (это уже изменение, требует отдельного согласования) либо собирать сразу после инцидента.

### 5.2 Состояние старого проекта
| Команда | Что даёт |
|---|---|
| `cat /etc/xray/state` | `mode` (vpn/direct) — что записано на Flash |
| `cat /etc/xray/emergency` | флаг аварийного режима, причина, время (объясняет L-01) |
| `cat /tmp/xray-state.vol /tmp/xray-wd.vol /tmp/xray-tproxy.sig /tmp/xray-tproxy.revert 2>/dev/null` | летучее состояние: `chosen`, `alive`, счётчики, подпись правил, дедлайн отката |
| `uci show xray` | фактическая конфигурация (URL подписки — **маскировать**) |
| `xray-tproxy status` | применена ли политика, есть ли расхождение nft/policy routing |
| `xray-manager status` | mode/effective/chosen/alive/rtt/direct |
| `xray-dns status` | какой upstream считает активным (с учётом B-04 — недостоверно) |
| `ps w | grep -E "xray|dnsmasq"` | какие процессы реально работают, их PID/VSZ |

| Команда | Что даёт |
|---|---|

### 5.4 Ошибки и устойчивость

## 6. Правила безопасности при сборе

1. **Только чтение.** Ни одна команда выше не меняет конфигурацию, не перезапускает службы, не устанавливает пакеты. `fw4 print` — печать, не применение; `nft list` — чтение.
2. **Не очищать журналы** (`logread -c` не использовать) — иначе потеряется история до инцидента.
3. **Маскировать секреты перед передачей:** UUID, `pbk`/`sid`, URL подписки с токеном, пароли PPPoE, приватные ключи. Практика: `sed -E 's#(vless|vmess|trojan|https?)://[^ "]+#<redacted-url>#g; s#(uuid|pbk|sid|password|token)[=:][^,} "]+#\1=<redacted>#g'`. Правило из `audit.sh:31-36` уже проверено.
4. **Не запускать команды, способные повлиять на связь** (никаких `fw4 reload`, `nft flush`, `ip rule del`, рестартов Xray/dnsmasq) до согласования.
5. **Не устанавливать диагностические пакеты** (`conntrack`, `iperf3`) без отдельного согласования — часть команд выше работает без них.

## 7. Как интерпретировать собранное (методика)

Чтобы не повторять ошибку «вывод по одному сообщению», при разборе:

1. Строить хронологию по **одному** источнику, затем сверять с другим (например, `xray-manager` ↔ `netifd`/`pppd`).
2. Для каждого события фиксировать: время, источник, безопасный фрагмент, вероятную причину, **степень достоверности** (высокая/средняя/низкая), последствия, решение, способ проверки.
3. Разделять: реальная ошибка / предупреждение / информационное сообщение.
4. Считать причиной только то, что подтверждается минимум двумя независимыми признаками (например, «правила сняты» + «watchdog: EMERGENCY» + «conntrack > 6000»).
5. Любое «вероятно» оставлять «вероятно» — как в документе №2, раздел H.
