# AGENTS.md — правила работы над VPN Manager для OpenWrt/Xray

Этот файл задаёт обязательные правила для разработчиков, coding-агентов и исполнителей документационных задач во всём репозитории. Он фиксирует согласованные границы проекта и рабочую дисциплину. Он **не заменяет** нормативную архитектуру, матрицу требований, API-контракты и тест-план проекта.

Если в подкаталоге есть дополнительный `AGENTS.md`, его правила применяются вместе с этим файлом. Подчинённый файл может уточнять локальные правила, но не может отменять решения владельца и общие запреты из этого документа.

> **Статус:** архитектурные решения U9 согласованы владельцем, но документальный комплект проходил независимое ревью и требовал корректировок. Наличие этого файла само по себе не означает, что все документы U9, код, сборка или целевой роутер уже проверены.

## 1. Главный принцип проекта

1. Максимально использовать штатные механизмы OpenWrt, Xray и уже используемых пакетов.
2. Не строить собственный фреймворк поверх OpenWrt/Xray.
3. Не добавлять собственные демоны, таймерные оркестраторы, постоянные менеджеры здоровья серверов, менеджеры DNS, менеджеры логов, event bus или универсальные абстракции без доказанной необходимости.
4. Если штатный механизм покрывает задачу, использовать его. Если не покрывает — сначала описать конкретный пробел и только затем предлагать минимальное расширение.
5. Не реализовывать функции «на всякий случай». Необязательные функции первого релиза не добавлять.
6. Исключённые функции не переносить в TODO, если владелец прямо не попросил сохранить напоминание.
7. Решения должны быть простыми, обозримыми, поддерживаемыми и соответствовать ограничениям OpenWrt-роутера, включая ограниченное хранилище и ресурсы.

## 2. Приоритет решений и работа с документацией

При обнаружении противоречий действуй в следующем порядке:

1. Последнее явно подтверждённое решение владельца.
2. Последние утверждённые нормативные документы и журнал решений проекта.
3. Действующие требования и архитектурные/API-контракты после проверки их актуальности.
4. Более ранние документы, U8/U7, patch и отчёты — только как история, если их решения заменены.

Правила:

- Не трактуй более позднее упрощение как ошибку предыдущей версии задним числом. Отмечай старое решение как `superseded`/историческое и указывай, чем оно заменено.
- Не удаляй историю решений и идентификаторы требований/сценариев бесследно. Не переиспользуй выведенные ID.
- Не считай шапку документа доказательством его актуальности: проверяй все действующие разделы, таблицы, примеры, JSON, схемы, API, ACL, UI и тесты.
- При изменении требования обновляй всю цепочку трассировки: README/обзор → архитектура → требования → модели и состояния → API/ACL → UI → план разработки → тесты/критерии приёмки.
- Поиск по репозиторию должен выявлять не только точные имена удалённых функций, но и их старые режимы, поля, методы, состояния, сценарии и остаточные зависимости.
- Если решение владельца отсутствует или формулировка неоднозначна, не выдавай свою догадку за согласованное требование. Зафиксируй вопрос/предложение отдельно.
- AGENTS.md — рабочие инструкции, а не повод переписывать нормативные документы без отдельного задания.

## 3. Архитектурные границы и исключённые функции

Следующие функции **не входят в v1** и не должны возвращаться в код, UI, API, модели, зависимости или активные требования без нового прямого решения владельца.

### 3.1. Полностью исключено

- Собственный AdBlock/Blocklists, списки рекламы и трекеров.
- Malware/Phishing-фильтрация и обещания защиты от неё.
- Загрузка, объединение, дедупликация, обновление и управление blocklists.
- Quick Block и связанная с ним логика.
- P4 / User BLOCK: собственная блокировка пользователей, её UI/API и отдельный аудит её наличия на роутере.
- P0 как режим/подсистема или отдельный менеджер трафика роутера.
- Собственный System Protected List, списки доменов/IP зеркал OpenWrt или системных обновлений.
- DNS Manager, Xray DNS, DoH/DoT, `https-dns-proxy`, собственный DNS fallback, DNS-фильтрация, отдельный DNS-кеш/TTL/инвалидация.
- Собственная серверная health-машина, `server_health`, `last_working_server`, отдельный failover/failback manager, собственные периодические retry-циклы.
- Пользовательский упорядоченный список приоритетов серверов.
- Собственная аналитика трафика, статистические агрегаты, экспорт аналитики, пользовательская лента событий/общий Journal.
- Мониторинг RAM/CPU/conntrack и ресурсный dashboard.
- Системные логи OpenWrt в UI, Telegram и другие расширенные каналы уведомлений.
- VPN-маршрутизация IPv6 в v1. Не менять и не отключать системный IPv6 роутера.
- Собственная ротация логов, log daemon или собственная система хранения архивов.

Не добавляй перечисленное в TODO «на будущее». Для фильтрации пользователь может самостоятельно использовать отдельные пакеты OpenWrt; приложение ими не управляет.

### 3.2. Не путать исключённые подсистемы с необходимыми проверками

- Отдельного P0 нет, но есть обязательное требование: **собственный исходящий трафик роутера не должен идти через VPN-туннель приложения и должен использовать штатную маршрутизацию OpenWrt**. Проверять это только в рамках аудита основной VPN-маршрутизации.
- Отдельного P4-аудита нет, но firewall и маршруты можно проверять в объёме, необходимом для корректной маршрутизации VPN-клиентского трафика и предотвращения обхода VPN.
- Не менять при таких проверках конфигурацию устройства.

## 4. Согласованная с владельцем сетевая модель

### 4.1. Для кого действует VPN

VPN-политика приложения применяется к клиентским устройствам/клиентскому трафику. Собственный исходящий трафик роутера не должен перехватываться VPN-приложением и остаётся на штатной маршрутизации OpenWrt.

Не проектируй отдельную P0-подсистему, отдельную маркировку системного трафика или специальные правила только ради старого P0.

### 4.2. Приоритеты маршрутизации

Сохраняй согласованную логику:

1. **Always DIRECT** имеет приоритет над VPN-политикой устройства и UDP allowlist.
2. UDP по умолчанию идёт DIRECT. Только явно разрешённые пользователем UDP-порты/диапазоны могут направляться в VPN-туннель.
3. UDP, не попавший в allowlist, идёт DIRECT, а не блокируется firewall.
4. TCP и DNS продолжают подчиняться ранее согласованной политике; правила UDP не должны незаметно менять TCP/DNS.
5. VPN-балансировщик применяется только к трафику, который после всех исключений действительно должен идти через VPN.

Не вводи старые режимы UDP `proxy/block/direct`, Quick Block или UDP firewall-blocking. Не создавай исключение UDP/443 по умолчанию.

### 4.3. DNS

В v1 все устройства, включая Always DIRECT, используют стандартный DNS роутера/OpenWrt. Не переключай DNS вслед за VPN и не добавляй собственные DNS-механизмы.

Пересмотр DNS (включая возможный Xray DNS и последствия для кеша) — отдельное напоминание перед выпуском, но не реализация v1. Не меняй DNS роутера без отдельного разрешения владельца.

## 5. Серверы, подписки и балансировщик Xray

### 5.1. Источник реализации

Используй штатные механизмы Xray: outbounds, `routing.balancers`, штатные стратегии, `observatory` и `fallbackTag`, если их поддержка подтверждена для целевой версии Xray. Не создавай собственный health/failover manager.

### 5.2. Автоматические стратегии

В UI показывай понятные названия, внутренние идентификаторы оставляй только в конфигурации:

- **Случайный выбор** → `random` (значение по умолчанию).
- **Распределять по очереди** → `roundRobin`.
- **По минимальному пингу** → `leastPing`.
- **`leastLoad` — выбор по доступной оценке Xray** → `leastLoad`.

Правила поведения и документации:

- Пользователь выбирает одну стратегию. Собственного списка приоритетов нет.
- `roundRobin` распределяет новые соединения между подходящими доступными outbound по кругу. Это не схема «первый сервер, а при отказе второй».
- `leastPing` выбирает по наблюдаемой задержке; не утверждай, что ping не влияет на выбор при этой стратегии.
- `leastLoad` описывай как выбор по доступной оценке Xray: при стандартном `observatory` используются доступные данные задержки. Не обещай измерение нагрузки или стабильности сервера и не называй его «самым стабильным»; ограничение показывай в UI и диагностике. `burstObservatory` в v1 не добавляется.
- Не добавляй пользовательские веса, коэффициенты и дополнительные параметры стратегий без необходимости и отдельного решения.

### 5.3. Observatory и fallback

Согласованная конфигурационная цель:

- Xray `observatory`;
- параллельные проверки: `enableConcurrency: true`;
- `probeInterval: "300s"`;
- использовать точное имя поля `probeUrl` (с маленькой `rl`), а не `probeURL`;
- рассмотренный probe URL `http://cp.cloudflare.com/generate_204` — кандидат, доступность и HTTP-ответ через фактический Xray outbound необходимо проверить;
- использовать `subjectSelector` так, чтобы он включал все серверные outbound и не захватывал посторонние outbound.

Не обещай проверку ровно каждые 300 секунд между началами циклов: при параллельном режиме Xray делает паузу после завершения набора проверок. Не обещай мгновенное обнаружение отказа. Учитывай поведение cold start: для `random`/`roundRobin` outbound без результатов наблюдения могут считаться доступными. Не добавляй собственную блокировку старта или health-state ради этого поведения.

`fallbackTag` должен применяться только к трафику VPN-балансировщика. Не используй безусловное правило на весь трафик, которое может перехватить Always DIRECT, UDP DIRECT, DNS или собственный трафик роутера.

Наблюдаемость состояния outbound (OQ-14, вариант B): только локальный gRPC `ObservatoryService.GetOutboundStatus` на `127.0.0.1`, в `api.services` только `ObservatoryService`. Ошибка создания listener — отказ запуска Xray (`ENGINE_DOWN`), а не `api_error`; loopback не является аутентификацией, локальный доступ и UID/GID фиксируются проверкой, а не предполагаются. Не включай `metrics`, `/debug/vars`, `StatsService`, `LoggerService`, `HandlerService`, `RoutingService` и не создавай HTTP-интерфейс приложения. API сообщает результаты наблюдения, но не выбранный outbound и не факт применения `fallbackTag`: такое состояние публикуй только как производное с явной пометкой.

Единственный экземпляр и конфигурация listener (U9-H3). Xray ставит `SO_REUSEPORT` на TCP-listener, поэтому занятость порта не защищает от второго экземпляра: одновременно допустим только один управляемый процесс, старый останавливается до запуска нового, совместное использование порта запрещено. `api.tag` непустой, `api.listen` — только литерал `127.0.0.1:<порт>`: пустое значение уводит commander на путь `OutboundListener`, `/` и `@` означают unix socket, `localhost`/IPv6/`0.0.0.0`/LAN-адреса запрещены. Блок `observatory` обязателен: без него `ObservatoryService` оставляет зависимость неразрешённой и ядро не стартует. Свежесть — по `last_try_time`, `TTL = T_cycle + grace`, `T_cycle ≤ probeInterval + 2 × max_probe_time` (concurrent) или `N × (probeInterval + max_probe_time)` (sequential), где `N` — число outbound после префиксного сопоставления. Не считай успешным откат на last-good, если он использует тот же занятый порт; вызов RPC выполняется с конечным дедлайном.

- `direct_on_failure` глобален для соответствующей VPN-конфигурации/подписки, не per-device; по умолчанию `true`.
- При `true` fallback для VPN-трафика — штатный DIRECT.
- При `false` fallback для этого VPN-трафика — штатный Xray `blackhole`; он не должен незаметно уйти в DIRECT или default outbound.
- Это не меняет обычный Always DIRECT и UDP DIRECT.
- Не создавай собственные блокирующие firewall-правила вместо Xray `blackhole`.

Технические свойства перечисленных полей и стратегий проверяй по документации и версии Xray, включённой в целевую сборку. Не считай ссылки на актуальную upstream-документацию доказательством наличия функции в старой/целевой сборке.

### 5.4. Ручной выбор конкретного сервера

Ручной выбор одного сервера сохраняется как отдельный **manual override**, независимый от автоматической стратегии:

- пользователь выбирает один конкретный сервер;
- выбор применяется немедленно;
- пока override активен, используется только выбранный сервер;
- при отказе выбранного сервера не перебирать другие VPN-серверы автоматически;
- при отказе использовать DIRECT или `blackhole` согласно `direct_on_failure`;
- возврат пользователя в автоматический режим снова включает выбранную стратегию Xray;
- после обновления подписки сохранять override, если выбранный сервер по-прежнему присутствует в новой подписке;
- сбрасывать override в автоматический режим только если выбранный сервер действительно исчез из успешно обновлённой подписки;
- не сбрасывать override просто из-за факта успешного обновления;
- при неудачном или пустом обновлении старая подписка и override сохраняются.
- технически override реализуется сужением `selector` балансировщика до тега закреплённого сервера: только так сохраняется штатный `fallbackTag`. Runtime-override Xray (`SetOverrideTarget`/`BalancerOverrider`) не использовать — он обходит `fallbackTag` и лишает ручной режим fail-closed.

Не превращай manual override в список приоритетов или собственный failover.

### 5.5. VLESS и подписки

- Одиночный `vless://...`: добавить → проверить подключение → использовать.
- Подписка: получить список реально возвращённых серверов; не добавлять серверы самостоятельно и не достраивать конфигурацию предположениями.
- Неудачное обновление или результат с нулём серверов — ошибка: сохранить прежний список и рабочую конфигурацию.
- После ошибки продолжать использовать сохранённые серверы; их доступность определяет штатный Observatory.
- Автообновление — отдельная галочка, по умолчанию выключена.
- Пользователь может выбрать интервал **6 / 12 / 24 часа**; значение в списке по умолчанию — 24 часа.
- Расписание реализовывать штатным механизмом OpenWrt (например, `crond`), не собственным daemon/timer manager.
- Ручное обновление доступно всегда.
- Не запускать немедленное первое обновление только по собственной инициативе, если оно прямо не закреплено актуальным решением/нормативным требованием. Неудачный запрос не порождает собственный цикл повторов: следующая попытка — по расписанию или вручную.

Сложное сопоставление серверов, fingerprint/identity framework, архивы подписок, восстановление неоднозначных конфигураций и elaborate retry queues не вводить.

## 6. Xray-логи

В v1 приложение работает только с двумя Xray-файлами:

- `/var/log/Xray/access.log`;
- `/var/log/Xray/error.log`.

Действующие функции:

- настройка штатного Xray `logLevel`;
- просмотр последних 20 / 50 / 100 строк;
- ротация обоих файлов штатным `logrotate`;
- общий для обоих файлов пользовательский порог размера в MB; значение по умолчанию — 5 MB;
- одна сжатая архивная копия на каждый файл; количество архивов не настраивается пользователем;
- проверка/ротация один раз в сутки; расписание не показывать в UI;
- применять `copytruncate`, чтобы Xray продолжал писать в тот же файл и не требовался перезапуск Xray;
- ручная очистка логов, включая очистку с сохранением N строк, в v1 отсутствует.

Технические ограничения:

- `copytruncate` имеет короткое окно между копированием и усечением файла; отдельные строки могут потеряться. Не скрывай это ограничение.
- Архивирование/сжатие требует временного дополнительного места на флешке. Проверяй это при расчёте дискового запаса.
- Проверяй штатную семантику `logrotate`: для «проверять раз в сутки и ротировать только при достижении порога» сверять `daily` и `minsize`; не подменять это сочетанием, которое меняет временную семантику.
- Конфигурация должна затрагивать только Xray-логи и не менять глобальную ротацию системных логов OpenWrt.
- Убедись, что пакет `logrotate` включён/доступен в целевой сборке, а расписание запускается штатным `crond`. Не считать пакет установленным на роутере без проверки.
- Ротацию нельзя реализовывать собственным скриптовым менеджером, если это умеет штатный пакет.

Другие системные логи, общий журнал событий и event feed в UI не добавлять.

## 7. Dashboard, статусы и уведомления

Главный экран показывает только важные предупреждения и критические ошибки состояния Xray, например:

- Xray остановлен/аварийно завершился;
- Xray не запустился после применения конфигурации.

Не трактуй произвольную строку в `error.log` как доказательство недоступности сервиса. Ошибки подписки и выбранного сервера показывай в соответствующих разделах. Не добавляй ленту событий, аналитику, мониторинг ресурсов или расширенные каналы уведомлений.

Оставляй только необходимые состояния самого Xray и краткоживущие состояния операций (например, обновление подписки). Не дублируй результаты Observatory в собственную машину состояний здоровья серверов.

## 8. OpenWrt: штатные механизмы и безопасность системных границ

По возможности использовать штатные компоненты OpenWrt:

- UCI — конфигурация;
- procd — жизненный цикл служб;
- ubus/rpcd и ACL — локальный API и авторизация;
- LuCI — веб-интерфейс;
- fw4/nftables и штатные `ip rule` / `ip route` / fwmark — клиентская маршрутизация, если подтверждено, что это необходимо;
- dnsmasq и штатный DNS OpenWrt — DNS в v1;
- `crond` — расписание подписки и logrotate;
- пакет `logrotate` — ротация Xray-логов.

Не добавляй прямые изменения в чужие подсистемы, сторонние DNS/AdBlock пакеты или глобальные системные настройки без отдельного разрешения.

### Запрет на изменение целевого роутера без разрешения

Без отдельного прямого разрешения владельца запрещено менять:

- UCI;
- firewall/fw4/nftables;
- `fwmark`, `ip rule`, `ip route`;
- DNS/dnsmasq;
- сетевые интерфейсы и параметры сети;
- IPv6;
- установленные пакеты и системные службы.

Аудит целевого устройства по умолчанию только read-only. Не выполнять перезагрузку, перезапуск сервисов, установку/удаление пакетов, применение конфигурации или тестовые изменения.

## 9. Безопасность и секреты

- Не выводить VLESS URI целиком, UUID, ключи, токены подписки, приватные данные и полные секретные конфиги в обычные логи, UI-ошибки, отчёты или тестовые фикстуры.
- Не добавлять секреты в Git, patch, screenshots или примеры документации.
- Санитизировать диагностические сообщения и ошибки провайдера подписки.
- Соблюдать принцип минимальных прав rpcd ACL: методы чтения не должны давать права изменения; write-методы выдавать только необходимой роли.
- API, ACL, UI и фактические ubus-методы должны совпадать. Не оставлять ACL для удалённых DNS/Blocklists-функций и не забывать права на действующие методы U9.

## 10. Порядок выполнения любой задачи

Перед началом изменений:

1. Прочитай этот `AGENTS.md` и относящиеся к задаче нормативные документы.
2. Проверь корень репозитория, рабочую ветку, HEAD, `git status`, локальные и неотслеживаемые изменения.
3. Определи, какие файлы являются нормативными источниками, а какие историческими.
4. Найди связанные требования, модели, состояния, API, ACL, UI и сценарии тестирования — не ограничивайся одним файлом.
5. Сформулируй минимальный объём изменений и список зависимостей до редактирования.

Во время работы:

- Не перезаписывай и не форматируй несвязанные файлы.
- Сохраняй исходную кодировку и окончания строк каждого файла (CRLF/LF), если изменение формата отдельно не требуется.
- Не применяй patch вслепую. Проверяй базовый commit/HEAD, контекст и `git apply --check` на предназначенной для этого копии.
- Не меняй одновременно несколько архитектурных вопросов без необходимости.
- Не добавляй зависимости, процессы, фоновые задачи и новые состояния без обоснования.
- Если кодовая реализация выходит за утверждённую архитектуру, остановись и явно опиши противоречие вместо того, чтобы молча расширять scope.

После работы:

1. Выполни релевантные unit/integration/config tests и проверки формата.
2. Выполни `git diff --check`.
3. Проверь устаревшие имена и поля исключённых функций, дублирующиеся JSON-ключи, ссылки на REQ/scenario IDs, синхронизацию API/ACL/UI и трассировку требований.
4. Для маршрутизации и Xray проверяй не только генерацию конфигурации, но и итоговую семантику правил, fallback и исключений.
5. Не утверждай, что проверка выполнена, если она только описана в тест-плане.
6. Отчёт должен отдельно указывать: базовый HEAD, изменённые файлы, команды и их фактические результаты, непроверенные пункты, известные риски и SHA-256 передаваемых артефактов, если они передаются.

## 11. Статусы готовности — не смешивать

В отчётах и документации различай:

- **Архитектурно согласовано** — решение принято владельцем.
- **Документально отражено** — действующие документы согласованы между собой.
- **Реализовано** — соответствующий код существует.
- **Сборка прошла** — сборка действительно выполнена успешно.
- **Проверено в тестовой среде** — тесты действительно запущены и прошли в описанной среде.
- **Проверено на целевом роутере** — проверено на целевой модели/прошивке с зафиксированными условиями.

Не повышай статус на основании одного только документа, статического анализа, успешного `git diff --check` или upstream-документации.

## 12. Технические проверки, которые нельзя считать выполненными заранее

Перед реализацией/приёмкой подтвердить на актуальной целевой сборке и версии Xray:

- версию Xray и поддержку `observatory`, `probeUrl`, `enableConcurrency`, `probeInterval`, четырёх стратегий, `fallbackTag` и `blackhole`;
- реальное поведение стратегий и Observatory при холодном старте и отсутствии probe-результатов;
- доступность и ответ probe URL через фактический VPN outbound;
- поведение новых и уже открытых соединений при отказе/восстановлении VPN и переключении DIRECT/blackhole;
- корректность manual override при обновлении подписки, включая сохранение при наличии сервера и сброс только при его исчезновении;
- исключение собственного трафика роутера из VPN на целевом OpenWrt без изменения его настроек;
- фактический порядок Always DIRECT, UDP allowlist, профильных правил и VPN-балансировщика;
- соответствие UDP-политики: allowlist в туннель, прочий UDP DIRECT, Always DIRECT выше allowlist;
- доступность `logrotate`, работу `crond`, корректную конфигурацию `daily` + `minsize`, одной сжатой копии и `copytruncate`;
- свободное место на флешке во время копирования/сжатия логов;
- точную синхронизацию методов API и rpcd ACL;
- наличие/поведение реального UDP-теста или тестового сервера в контролируемой среде.

Проверка целевого роутера по умолчанию read-only. Тесты, требующие изменения устройства, выполняются только после отдельного явного разрешения.

## 14. Критерий качественного решения

Решение считается подходящим для проекта, если оно:

- использует штатный механизм, когда тот применим;
- не возвращает исключённые функции и старые состояния;
- не создаёт лишние демоны, циклы, менеджеры и зависимости;
- согласовано с требованиями, архитектурой, API, ACL, UI, моделями и тестами;
- безопасно обращается с VPN-секретами и ограниченным хранилищем роутера;
- не меняет систему вне явно разрешённых границ;
- имеет честно обозначенный статус проверки и воспроизводимые результаты.
